# План: рефакторинг агентов на Plan → Execute + упрощение

Статус: реализован (ветка refactor/agent-plan-execute, этап проверки)

Цель: убрать костыли-гарды и дублирующие тулы, добавить явное двухфазное
планирование (Plan → Execute), серверную блокировку отправки при обработке,
универсальное токен-сжатие. Сохранить домен-деление и приоритет мозга.

---

## 0. КОНТЕКСТ — что за проект, в чём проблема и почему так

### Проект
Next.js 16 + React 19 + TypeScript + Ant Design, FSD-архитектура,
Prisma + SQLite, пакетный менеджер **pnpm**. RPG-платформа: ИИ-мастер
(Game Master) ведёт настольную игру. Три чата:
- **Общий игровой** — GM игрового чата (`runGameMasterBatch`);
- **Личный** — GM личного чата с игроком (`runGameMasterPersonal`);
- **Builder** — настройка игры админом в dev-режиме (`runBuilderAgent`).

Агенты построены на **Vercel AI SDK** (`generateText` + tool-calling),
модель **deepseek-v4-flash** (быстрая/средняя). Документы хранятся в БД
(SQLite, таблица `Document`) как markdown, категории: `glossary` (глоссарий,
read-only в игре), `brain` (мозг — инструкции GM), `game_hidden` (скрытые
заметки GM), `game_visible` (данные игроков: листы персонажей, инвентарь).

### История проблем (почему это всё накопилось)
1. **GM забывал важные факты.** Раскрыл в чате «сейф за картиной», а через
   время говорил «под половицей». Причина: скрытая память не велась — окно
   последних ~30 сообщений + авто-саммари не сохраняли сюжетные факты.
2. **GM писал «Кнопка готова — Расследование (1d20+2)» текстом, но НЕ
   вызывал `present_roll_check`** → кнопки не появлялось. Подтверждено
   логом `logs/gm-game.log`: в типичном сбое `actions=[get_player_sheet,
   get_rolls]`, ролл не создан, а в тексте обещание кнопки.
3. В попытке лечить эти две проблемы **наслоили костыли**:
   - `send_reply` + `review_draft` — модель их **игнорирует** (за всё время
     ни разу или 1 раз в логе); доставка всегда шла через `result.text`;
   - `update_memory` — **дублировал** `write_note`/`update_document`, модель
     его не вызывала (0 вызовов в логе, документа «Game Memory» нет);
   - **ролл-гард** и **memory-гард** — keyword-эвристики по тексту
     (`promisesRoll`, `revealsPlotInfo`), ретраи с коррекцией.
4. Дополнительно найдено и уже частично починено:
   - роллы мастера (`roll_dice`) не показывались в чате (`completedAt` не
     ставился) — **уже исправлено**;
   - GM не умел **удалять** документы (нет `delete_document` у GM);
   - `read_document` у GM не умел читать по секциям (offset/limit есть
     только у билдера);
   - серверные экшены отправки **не блокируют** отправку во время
     обработки (блокирует только клиент через `typing`).

### Вывод / зачем Plan → Execute
Костыли-гарды и дублирующие тулы запутывают модель и код. Правильный
паттерн хороших агентов (Kilo/Claude Code, LangGraph, OpenAI Agents) —
**явное двухфазное планирование**: (1) изучи и спланируй (read-only),
(2) выполни план (запись + броски + ответ). Тогда «забыл выдать бросок»
решается структурно: бросок запланирован в фазе 1 и исполняется в фазе 2,
без гардов и keyword-эвристик. Плюс: серверная блокировка отправки при
обработке делает ненужным рекурсивный batch, а токен-сжатие нужно
универсально (как в популярных агентах), а не только у билдера.

### Что уже есть и НЕ ломаем
- **Домен-деление:** `search_rules` (только глоссарий, сниппеты),
  `get_brain` (мозг: `_index` возвращается первым), `get_gm_notes` /
  `get_scene_state` (game_hidden), `get_player_sheet` (game_visible).
- **Приоритет «Мозг (brain) FIRST»** — в обоих GM-промтах.
- **Ролловый флоу:** `present_roll_check` / `get_rolls` / `confirm_rolls` /
  `remove_roll`; завершённые роллы встраиваются в контекст как последние
  user-сообщения; новые сообщения помечаются 🆕; роллы мастера показываются
  как «🎲 Мастер: результат» без подписи.
- **Лог `logs/gm-game.log`** (диагностика) + action-ledger
  (`reply-tools.ts`: `clearActions`/`recordActions`/`getActions`).
- **«tools are invisible»** (не описывать вызовы тулов в тексте ответа).
- **Билдер:** режимы brain/memory, сжатие через `prepareStep`, импорт файлов
  (архив — НЕ трогаем).

### Что должен дать итог
1. Два прохода Plan → Execute во всех трёх чатах.
2. Серверная блокировка отправки при обработке → убрать рекурсивный batch.
3. Универсальное токен-сжатие (общий модуль) для билдера и GM.
4. Удалить: `update_memory`, `send_reply`, `review_draft`, ролл-гард,
   memory-гард, `promisesRoll`, `revealsPlotInfo`, `didCallSendReply`.
5. Добавить: GM `delete_document` (нельзя глоссарий/мозг), `read_document`
   offset/limit (формулы считаются на всём документе), список партии в
   памяти, гейт «пустой вызов».
6. Промты GM: порядок ведения памяти (изучи → реши → индекс → лист/себе).

### Важно для исполнителя
- Работать строго по разделам ниже; перед началом прочитать
  `docs/GOLDEN-RULES.md`, `docs/CODING.md`, `docs/ANTI-PATTERNS.md`,
  `docs/SERVER-ACTIONS.md`.
- Проверять после каждого этапа: `pnpm exec tsc --noEmit` и
  `pnpm run lint`. Dev-сервер агент НЕ запускает (запускает пользователь).
- Файл лога `logs/gm-game.log` — диагностика, gitignore'ится.
- Ограничение окружения: правки разрешены только в `.kilo/plans/*.md`;

## 1. Архитектура ответа — два прохода generateText

**Проход 1 — «Изучи и спланируй» (read-only тулы):**
- Тулы: `search_rules`, `get_brain`, `get_gm_notes`, `get_scene_state`,
  `get_player_sheet`, `read_document`, `get_rolls`, `get_players`,
  `get_chat_summary`.
- Промт (append к системе): «Ты в фазе ПЛАНИРОВАНИЯ. Изучи ситуацию
  (мозг-индекс первым, затем нужные документы). Ничего не пиши, броски не
  выдавай, в чат не отвечай. Верни план по шаблону:
  STUDY: <что изучил> | RECORD: <что и куда записать> | ROLLS: <какие броски> |
  REPLY: <outline ответа>. План краткий (до ~400 слов).»
- Результат: `planText` (текст).

**Проход 2 — «Выполни план» (полный набор тулов):**
- Промт (append): «Фаза ВЫПОЛНЕНИЯ. Выполни план строго: <planText>.
  Запиши память/лист как в плане, выдай запланированные броски
  (present_roll_check), затем напиши финальный ответ — это текст, который
  увидит игрок.»
- Результат: `gmText` = `result.text`.

**Гейт «пустой вызов»:** если нет новых сообщений игроков И нет
завершённых необработанных роллов → Pass 1 пропускаем, один короткий вызов
с пометкой «Новых сообщений и бросков нет. Не придумывай действия — кратко
спроси игрока, что он хочет делать».

**Доставка:** всегда `result.text`; если пусто → ретрай (полные тулы,
коррекция «напиши полный ответ»); fallback-сообщение; save + broadcast.

## 3. Серверная блокировка отправки при обработке

Сейчас: клиент блокирует ввод при `typing`, но серверные экшены отправки
НЕ проверяют обработку → сообщения могут приходить во время генерации.

Добавить:
- GM: экспортировать `isProcessing(sessionId)` (по `getGuard()`) из
  `gm-runner.ts`.
- В `sendGameMessageAction`, `sendPersonalMessageAction`,
  `sendBuilderMessageAction`: если `isProcessing(sessionId)` → вернуть
  ошибку «идет обработка, подождите» (новый i18n-ключ
  `chat.processingBlocked`).
- Builder: уже есть `isProcessing` в builder-runner — использовать в
  `sendBuilderMessageAction`.

Следствие: новых сообщений во время генерации не бывает → **рекурсивный
batch удалить** из `runGameMasterBatch`.

## 4. Универсальное токен-сжатие

Вынести сжатие из билдера в общий модуль (например,
`src/shared/lib/agents/context-compress.ts`):

```
compressMessages({ messages, steps, threshold, maxTokensPerMsg }) →
  { messages: compressed } | null
```

- Логика (как у билдера): оценить токены (`chars/4`), если > порога
  (`contextLimit × 0.7`) → system + последнее user-сообщение + последний
  tool-шаг + сводка остального («Создано N, обновлено M, искал K»).
- Использовать в:
  - билдере (заменить его inline-prepareStep на общий модуль);
  - GM игровой и личный (`makePrepareStep` перестаёт быть пустышкой —
    подключает общий компрессор).

## 10. Что может сломаться / проверить после рефактора

1. **Латентность ×2** — два вызова на ответ. Бабл «думает» дольше; для
   flash терпимо. Проверить UX.
2. **Пустой план** — если Pass 1 вернул пусто → пропустить инъекцию,
   Pass 2 без плана (не падать).
3. **Pass 1 не должен писать** — read-only набор тулов; проверить, что
   write/roll-тулов нет в `getPlanTools`.
4. **Ролловый флоу** — завершённый ролл входит user-сообщением в оба
   прохода. Проверить: Pass 1 видит результат и планирует, Pass 2
   обрабатывает; без дублей.
5. **Ретрай «пустого ответа»** — только в Pass 2; бабл не гаснет молча.
6. **Серверная блокировка** — при обработке отправка возвращает ошибку;
   клиент и так блокирует ввод. Проверить сообщение игроку.
7. **Удаление рекурсивного batch** — убедиться, что сообщения не
   «зависают» (блокировка это гарантирует).
8. **Сжатие GM** — порог/качество; длинные диалоги не рвутся, текущий
   tool-шаг не сжимается. Билдер не регрессирует.
9. **delete_document у GM** — глоссарий/мозг нельзя удалить,
   game_hidden/game_visible можно.
10. **read_document offset/limit** — формулы от полного документа, текст по
    куску; whole-read не сломан.
11. **i18n/доки** — tsc + lint + grep: нет ссылок на удалённые ключи/тулы.
12. **Лог gm-game.log** — обновить под два прохода (PLAN/EXEC).
13. **«Мозг первым»** — в Pass 1 первым вызывается `get_brain` (по логу).
14. **Память/лист** — раскрытие факта → RECORD в плане + реальная запись
    в Pass 2.
