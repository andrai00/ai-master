# Открытые вопросы и риски

Это НЕ решённые проблемы. Их надо будет разбирать перед соответствующим этапом разработки.

---

## 1. Движок формул: граф зависимостей и циклические ссылки

**Формулы ссылаются на формулы.** Атака = база + бонус_оружия + эффекты. Эффекты временные. При изменении любого поля — пересчёт всего что от него зависит.

**Сложности:**
- Циклические зависимости (A зависит от B, B зависит от A) — детектить и запрещать.
- Кросс-листовые ссылки: характеристика корабля зависит от навыка пилота, а навык пилота в листе персонажа.
- Условные формулы: "если уровень > 5 то +2 иначе +1".
- Формулы внутри формул внутри эффектов. Глубина вложенности.

**Варианты:** `mathjs` с кастомным графом зависимостей. Или свой мини-интерпретатор с поддержкой `1d6`, условий, ссылок `$player.dex`.

**Вопрос:** нужен ли компилятор формул в AST или достаточно eval-подобного выполнения каждый раз? (AST — быстрее при пересчёте, eval — проще для динамических формул от нейронки.)

## 2. Безопасность скрытой информации

Game Master знает: игрок A крадёт у игрока B. Он должен сказать B "сделай проверку восприятия" не раскрывая причину, и в общем чате не проговориться.

**Проблема:** LLM не детерминирована. Она может случайно вставить "потому что A крадёт твой кошелёк" в сообщение.

**Варианты:**
- Пост-фильтр: перед отправкой в чат проверять не раскрывает ли сообщение скрытую информацию (но как? ещё одна LLM? правила?)
- Маркировка сообщений: Game Master помечает сообщение как "приватное" или "общее", платформа проверяет адресата.
- Разделение контекстов: Game Master для каждого чата = отдельный вызов LLM со своим контекстом, без кросс-контаминации.

**Сложность:** даже раздельные вызовы не гарантируют что агент не "вспомнит" лишнего из других чатов внутри одного вызова.

## 3. Миграции при правке мастера

Админ поправил правила во время кампании. У игроков уже есть персонажи, инвентарь, активные эффекты.

**Что надо сделать:**
- Понять какие именно листы и данные затронуты изменением
- Предложить админу: "затронуто X листов, Y эффектов. Обновить?"
- Применить изменения не ломая существующие данные
- Сохранить возможность отката

**Сложности:**
- Builder должен понимать семантику своих же изменений ("я поменял формулу расчёта атаки, значит все листы где есть атака — затронуты")
- Частичное обновление: пересчитать атаку но не трогать инвентарь
- Версионирование: как сделать снапшот до и после? Git под капотом? Свои снапшоты?
- Атомарность: если миграция сломалась посередине — не оставить систему в поломанном состоянии

---

## 4. Конкурентный доступ (несколько игроков)

Два игрока одновременно пишут в личку Game Master'у. Оба хотят что-то сделать с общим инвентарём.

**Проблемы:**
- Одна LLM-сессия vs несколько параллельных? Если одна — как разрулить очередь? Если несколько — как синхронизировать файлы?
- Race condition: два агента читают `data.yaml`, оба пишут изменения, один перезаписывает другого.
- Блокировки на файлы? Оптимистичные блокировки с версиями?

**Варианты:**
- Очередь запросов: строгий порядок, медленно но безопасно.
- Несколько сессий Game Master с общей файловой системой + локи (`.lock` файлы).
- Событийная модель: Game Master получает события, обрабатывает последовательно.

## 5. Детерминизм правил vs галлюцинации LLM

Builder может неверно понять правило. Game Master может неверно его применить. И так всю кампанию — игроки думают что всё по правилам, а нет.

**Риски:**
- Builder при парсинге PDF пропустил предложение и "додумал"
- Game Master неправильно интерпретировал формулу
- Правила противоречивы в оригинале → Builder выбрал одну трактовку, админ не заметил

**Как снизить (не решить полностью):**
- Builder всегда сохраняет ссылку на источник — админ может перепроверить
- Game Master логирует все применения правил — аудит постфактум
- Тестовые сценарии: Builder создаёт "проверочный персонаж", админ сверяет с эталоном
- Ограничение: **мы не можем гарантировать 100% правильность**, это свойство LLM

## 6. Эмбеддинги: online (API) vs offline (локально)

Для семантического поиска правил нужны эмбеддинги.

**Online (OpenAI `text-embedding-3-small`):**
- + Качество, скорость, не грузит CPU
- - Нужен интернет, нужен API-ключ, платно, данные уходят наружу

**Offline (`@xenova/transformers` / Transformers.js):**
- + Полностью локально, приватно, бесплатно
- - Медленнее, грузит CPU/память, качество ниже на русском (модели в основном английские)

**Вопрос:** хотим ли мы полностью локальную работу без внешних API? Если да — придётся мириться с ограничениями локальных эмбеддингов. Если нет — OpenAI embeddings. Компромисс: оффлайн по умолчанию, опциональный online.

## 7. Версионирование и откат

Нужно ли версионирование файлов? Для миграций — да. Для отладки — полезно. Для "ой я всё сломал" — критично.

**Варианты:**
- Git под капотом: `simple-git`, каждый важный шаг = коммит. Плюс: бесплатно, привычно. Минус: бинарные артефакты (.index/), сложность с конкурентным доступом.
- Свои снапшоты: копия папки с таймстемпом. Плюс: просто. Минус: занимает место, нет диффов.
- Журнал изменений: писать только дельты, не хранить полные копии. Плюс: компактно. Минус: сложно реализовать.

**Вопрос:** насколько частыми будут откаты? Если редко — простых снапшотов хватит.

## 8. Composite-документы: разрешение конфликтов слоёв

Разные слои могут давать конфликтующие модификаторы к одному полю:

- Раса эльф: +2 ловкость
- Проклятье: -1 ловкость
- Амулет: +1 ловкость
- Эффект благословения: +2 ко всем проверкам (включая ловкость?)

**Вопросы:**
- Порядок применения слоёв важен? (базовый → раса → класс → уровень → эффекты?)
- Как обрабатывать "переопределение" vs "накопление"? (эльф говорит +2, другой слой говорит "ловкость = 10" — это переопределение или база?)
- Временные эффекты: как понять что эффект истёк? По раундам? По реальному времени? По событию?

## 9. Гранулярность прав доступа

Общий лист (корабль): пилот меняет курс, инженер — энергию, пассажиры — ничего.

**Вопросы:**
- Права на уровне секций внутри одного листа? Или права только на уровне файлов?
- Кто настраивает права? Builder при создании мастера? Админ руками?
- Как Game Master проверяет права? Перед каждым изменением сверяется с `config.yaml`?

## 10. Качество повествования (не техническая проблема)

Сможет ли LLM вести игру увлекательно, а не механически "сделай бросок → получил 15 → прошло"?

**Риски:**
- Генерация однотипных ответов
- Потеря нити сюжета на длинной дистанции
- Неумение импровизировать когда игроки делают неожиданное

**Частичные решения:**
- Скил `scene-narration` с примерами хорошего повествования
- Разнообразие через температуру/частоту модели
- Инъекция "сюжетных хуков" из долгосрочной памяти

Но это — качественная проблема, не чисто техническая. Будет требовать итеративной настройки промптов.

## 11. Контекстное окно: адаптация под разные модели

Claude: 200K токенов. GPT-4: 128K. Локальные Llama/Mistral: 8K–32K.

Стратегии progressive disclosure должны работать на **минимальном** окне (8K–32K). Нельзя полагаться на 200K.

**Вопрос:** насколько агрессивно резать контекст? Саммари каждые 5 сообщений? 10? Адаптивно?

---

## 12. Формулы и броски: встраивание в Markdown

Как именно выглядит кнопка броска в чате? Какой синтаксис?

Варианты:
- `[🎲 D20+5]` — расширение Markdown
- `<!-- roll:D20+5:проверка скрытности -->` — скрытый маркер
- `:::roll Проверка скрытности | D20+5` — callout-синтаксис

Важно: синтаксис должен быть **устойчив к ошибкам нейронки** — если она сгенерировала кривой синтаксис, рендерер не должен падать, а показать как текст.

## 13. Структурирование правил: что если игра огромная

Pathfinder 2e, D&D 5e со всеми дополнениями — тысячи страниц. Builder физически не сможет всё это обработать за разумное время/бюджет API-токенов.

**Вопросы:**
- Приоритезация: обрабатывать только то что админ отметил как важное?
- Инкрементальная загрузка: сначала core book, потом дополнения по запросу?
- Кэширование: если правила уже структурированы — шарить между админами?
