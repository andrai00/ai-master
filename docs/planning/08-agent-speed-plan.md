# План: перевести агентов на архитектуру Cursor / Kilo Code (1-в-1, с разделением чата и внутрянки)

> Дата: 2026-08-20. Статус: план, правки не начаты.
> Требования:
> 1. Продолжение чата после рестарта — **1-в-1 как у Cursor**: модель видит весь транскрипт сессии (сообщения + все вызовы тулов + все результаты + прочитанные документы).
> 2. **Изучение и чаты — отдельно.** В чате видна только история итогов (как сейчас). Вся внутрянка (тул-колы, аргументы, результаты, промежуточный текст) хранится отдельно и видна **только через отдельный env-режим для дебага** — то, что у Cursor/Kilo Code показано в UI.
> БД можно менять.

## 1. Сейчас: почему не 1-в-1 с Cursor

1. В БД хранятся только итоговые сообщения. Вызовы тулов и результаты живут только в памяти генерации и исчезают при рестарте.
2. Контекст каждого раунда собирается заново (последние 20–30 сообщений + динамика). «Что изучал ранее» — теряется.
3. Двухфазный plan→exec — самодельная надстройка, которой нет у Cursor (там единый цикл).

## 2. Целевая архитектура

### 2.1. Разделение: `Message` (чат/итоги) + `AgentTranscript` (внутренности)

- **`Message`** — как сейчас: только итоговые сообщения чата. Пользовательский интерфейс и история **не меняются** (никаких фильтров по kind, никаких технических строк).
- **`AgentTranscript`** — НОВАЯ таблица: полный ход каждого раунда (что модель читала, какие тулы звала с какими аргументами, что получила, промежуточный текст). Это «внутренности», которые у Cursor/Kilo видны в чате, а у нас — только в debug-режиме.

```prisma
model AgentTranscript {
  id         String   @id @default(uuid())
  sessionId  String
  runId      String               // id раунда (связь с Message.runId)
  seq        Int                  // порядок строк внутри сессии
  kind       String               // "user" | "text" | "tool-call" | "tool-result"
  toolName   String?              // имя тула (tool-call)
  toolCallId String?              // связь call ↔ result
  args       String?              // JSON-вход тула
  result     String?              // результат тула
  content    String?              // текст (kind = user / text)
  messageId  String?              // ссылка на Message (для user/final строк)
  status     String   @default("done")  // "done" | "aborted"
  summarized Boolean  @default(false)
  createdAt  DateTime @default(now())

  @@index([sessionId, seq])
  @@index([runId])
}
```

**Message** получает одну колонку `runId String?` — группировка сообщений по раунду (для сборки контекста и каскадной очистки). Остальное в Message не меняется.

### 2.2. Запись транскрипта (`persistRun`)

В конце раунда (успех или стоп пользователя) одним batch-insert в транзакции:

- 🆕 user-сообщения раунда → в `Message.runId` проставляется id раунда;
- каждый tool-call → `AgentTranscript{ kind: "tool-call", toolCallId, toolName, args }`;
- каждый результат → `AgentTranscript{ kind: "tool-result", toolCallId, result }`;
- финальный текст → `Message{ role, runId }` + `AgentTranscript{ kind: "text", messageId }` (копия для транскрипта).
- При ошибке — ничего не пишем (транзакция откатывается).
- Запись атомарна: весь раунд либо в БД, либо ничего.

**Остановка пользователем (стоп):** раунд пишется в БД с `status: "aborted"` (то, что успело — все тул-колы, результаты, частичный текст). Эти строки:
- **исключаются** из сборки контекста (см. 2.3) — следующий ход начинается **заново с нового сообщения**, как сейчас;
- сохраняются **только для debug-режима** (видно, где остановился);
- промежуточный текст в чат (`Message`) не пишется.

### 2.3. Сборка контекста (`buildTranscript` — реконструкция как у Cursor)

- Читаем не-summarized `Message` + не-summarized `AgentTranscript` сессии, **исключая строки со `status: "aborted"`** (остановленные раунды в контекст не попадают).
- Мержим по `runId`: для каждого раунда — его user-сообщения, затем tool-call/tool-result строки, затем финальный текст. Порядок раундов — хронологический по `Message.createdAt`.
- Реконструируем `ModelMessage[]` (parts-формат AI SDK v7):
  - text → `parts: [{ type: "text", text }]`,
  - подряд идущие `tool-call` → assistant с `parts: [{ type: "tool-call", toolCallId, toolName, args }]`,
  - `tool-result` → user с `parts: [{ type: "tool-result", toolCallId, toolName, output }]`.
- Динамические блоки (прелоад мозга, броски, 🆕-разметка, ChatSummary) собираются заново, в БД не пишутся.
- Итог: после рестарта модель видит **тот же транскрипт**, что и до него — продолжение 1-в-1 с Cursor.

### 2.4. Единый агентный цикл (single loop)

Как у Cursor: один `streamText` с полными тулами на весь ход. Модель сама читает → пишет → отвечает.

**Унифицируется ТОЛЬКО механика цикла** (один вызов + транскрипт + стриминг). Промпты, тулы и режимы каждого чата **остаются своими** — это разные агенты для разных задач:

| Чат | System-промпт (остаётся) | Тулы (остаются) | Динамический контекст (остаётся) |
|-----|--------------------------|-----------------|----------------------------------|
| Builder | `loadSystemPrompt()` + `{builderMode}` (BRAIN / MEMORY) | `getTools(builderMode)` — наборы для brain и memory | `buildContext` (прелоад мозга, саммари, 🆕) |
| GM игровой | `GM_GAME_SYSTEM` | `getGameTools()` — вкл. `set_scene_state`, `get_players`, игровые броски | `buildGameContext` (броски, сцена, игроки) |
| GM личный | `GM_PERSONAL_SYSTEM` | `getPersonalTools()` — personal-броски, без `get_players`/`set_scene_state` | `buildPersonalContext` (playerId, личные броски) |

**Удаляются ТОЛЬКО двухфазные промпты-оркестрация** (`BUILDER_PLAN_SYSTEM`, `GM_PLAN_SYSTEM*`, `PLAN/EXEC_SYSTEM_PROMPT`), обязательные plan-наборы (`getPlanTools`, `STUDY_TOOLS`, `BUILDER_STUDY_TOOLS`) и `study-summary.ts` — в single loop перечитывание не проблема (всё в транскрипте), study-summary был костылём. `getPlanTools` вернётся в Фазе 3 как read-only набор для plan-режима (свой для каждого чата).

### 2.5. Компрессия и автосуммаризация

- **Внутри раунда:** `compressMessages` (порог `min(limit×0.7, 24000)`) сжимает старые шаги — как сейчас.
- **Между раундами:** `runChatSummarizer(masterId)` — фоновый вызов LLM без тулов: `[старый ChatSummary] + [не-summarized сообщения] → [новый ChatSummary]`. Триггер: ≥20 не-summarized `Message`. После записи помечаем `summarized: true` всю волну: `Message` + соответствующие `AgentTranscript` (по `runId`). Сжатая волна не читается при сборке контекста — её место занимает `## Chat History Summary` (как Cursor при превышении окна).

### 2.6. Стриминг (внутренний; игрокам — как сейчас)

`streamText` используется на сервере (быстрый первый токен, сбор финального текста, persist). Чанки → событие `text` в step-tracker → Socket.IO (комната `steps:{sessionId}`).

**Отображение:**
- **Игроки / обычный режим** — видят то же, что и сейчас: «облачко» с подписями шагов-тулов, затем готовое итоговое сообщение целиком. Никакого частичного текста.
- **Debug-режим** (`AGENT_DEBUG=1` + админ) — в облачке/под сообщением виден живой текст и вся внутрянка.

В БД текст пишется один раз по завершении (`Message` + транскрипт).

### 2.7. Plan mode (переключатель, как у Kilo/Cursor)

- UI-переключатель Plan/Agent в Builder-чате и игровом чате (админ).
- **Plan mode:** single loop, только read-тулы, промпт «выдай план, ничего не меняй». Результат — `Message{ plan: true }` → карточка «План».
- **Agent mode** (по умолчанию): полный цикл; последний план инжектится блоком `## Plan to execute`.
- Для этого колонка `Message.plan Boolean @default(false)`.

### 2.8. Журнал изученных документов `DocumentRead`

> **Важно:** `DocumentRead` — это **НЕ хранилище изученного содержимого**. Изученное содержимое хранит транскрипт (`AgentTranscript`, раздел 2.3). `DocumentRead` — вспомогательный **индекс-подсказка**: список id документов + дата чтения. Он нужен только после того, как старый транскрипт сжат компрессией, — чтобы модель знала «ты уже читал X, не изменился» и решила, перечитывать ли. У Cursor аналога нет (он просто переоткрывает файл); у нас это дешёвая оптимизация, а не механизм памяти.

```prisma
model DocumentRead {
  id         String   @id @default(uuid())
  sessionId  String
  documentId String
  readAt     DateTime @default(now())
  @@unique([sessionId, documentId])
}
```
- Запись при `read_document` / `get_brain` / `get_gm_notes` / `get_player_sheet` / `get_scene_state` (пакетно в конце раунда).
- В контекст инжектится компактный блок «Ранее прочитанные документы этой сессии: [title (id), изменён после чтения: да/нет]» — для контента, уже сжатого компрессией, и для контроля изменений (правило 2.4 Фазы 4).

### 2.13. Память как у Cursor/Claude/Kilo — три слоя (с хранением в БД)

Ключевой вопрос: «как ИИ хранит изученное?». Никакой магии — ровно как Cursor, только вместо файла-транскрипта в памяти — таблицы в БД:

| Слой | Как у Cursor/Claude/Kilo | У нас в БД | Что это |
|------|--------------------------|------------|---------|
| 1. Рабочая память (полный транскрипт: все сообщения + результаты чтений + тул-колы) | транскрипт сессии, живёт в памяти IDE | `AgentTranscript` + `Message` | **это и есть «память изученного»** |
| 2. Сжатая память (auto-compact) | старые сообщения сжимаются в саммари внутри транскрипта | `ChatSummary` (+ `compressMessages` внутри раунда) | когда контекст переполняется |
| 3. Источник (сами файлы/документы) | файлы на диске | `Document` (все категории) | не хранятся в транскрипте, читаются тулами |
| 4. Подсказка «что я читал» | нет как таковой (переоткрывает файл) | `DocumentRead` (опционально) | только оптимизация после сжатия |

**Как это работает по шагам (пример):**

1. Агент прочитал документ X (тул `read_document`) → **содержимое X сохраняется в `AgentTranscript`** (kind: tool-result). Это то же, что у Cursor: прочитанный файл остаётся в истории сессии.
2. Следующий ход (и после рестарта): `buildTranscript` собирает из БД этот результат → **модель видит содержимое X, не перечитывая его**. Ровно как Cursor продолжает с того же места.
3. Контекст переполнился → старые волны сжимаются в `ChatSummary` (содержимое X уходит из промпта, остаётся суть). Как auto-compact у Cursor.
4. Понадобился X снова → один тул `read_document` перечитывает X из БД (как Cursor заново открывает файл). `DocumentRead` подсказывает: «X уже читал, не менялся» — чтобы не перечитывать зря, если суть уже есть в саммари.

**Итог:** мы воспроизводим ровно тот же механизм, что у Cursor/Claude/Kilo (транскрипт → компакт → файлы на диске), но вместо памяти IDE и файлов — таблицы SQLite. Даже надёжнее: транскрипт в БД переживает перезапуск, а у Cursor транскрипт — до закрытия окна (частично восстанавливается из сессии).

### 2.9. Debug-режим: внутрянка как у Cursor/Kilo, только по env

Вся внутрянка уже в `AgentTranscript`. Показывается **только при `AGENT_DEBUG=1`** (env на сервере):

- Новый server action `getAgentTranscriptAction(sessionId)` — отдаёт строки транскрипта (включая `status: "aborted"` — видно, где остановился раунд). Доступ: `AGENT_DEBUG=1` И роль admin.
- В UI (chat-panel) — при `AGENT_DEBUG=1`: живой стрим текста в облачке + сворачиваемый блок внутрянки под каждым итоговым сообщением (тул-колы с аргументами, результаты, промежуточный текст) — как у Cursor/Kilo. В обычном режиме — только «облачко» шагов, как сейчас.
- Без env-флага блок не рендерится и action возвращает отказ. Итоговая история чата при этом **не меняется** (только `Message`, как сейчас).

### 2.10. Мозг, глоссарий и другие документы — внешняя память, суммаризация их не трогает

- **Суммаризация сжимает ТОЛЬКО переписку** (`Message` + `AgentTranscript`). Мозг, глоссарий, заметки и листы — `Document`-документы в БД; они не участвуют в суммаризации и никогда не «теряют память».
- **Мозг** — прелоад остаётся: индекс + сводки секций всегда в контексте; полная секция — по `get_brain(topic)` / `read_document`. Мозг целиком никогда не грузится (G42: секции ≤6–7 КБ, индекс 3–5 КБ). Забыл секцию → доизучает тем же тулом (1 шаг).
- **Глоссарий** — как сейчас: `glossary_overview` (счётчики по типам) + `search_rules` (точечный поиск) + чтение найденной статьи. Жёсткие правила: модель ищет правило, только когда оно нужно, читает только найденное и опирается на него.
- **«Не выдумывать правила»** — четыре механизма:
  1. Промпт: «для механики/чисел/эффектов — `search_rules`; никогда не додумывай правило, которого нет в контексте».
  2. Транскрипт: прочитанное правило персистентно остаётся в контексте раунда и следующих ходов.
  3. `DocumentRead`: после сжатия старого чата модель знает «ты читал документ X, не изменился» → перечитывает при необходимости.
  4. Компрессия не трогает документы — сжимаются только старые шаги переписки.
- **Сюжет — можно выдумывать**: мозг = процедуры (как вести), глоссарий = механика (числа/эффекты — тут без выдумок), `game_hidden` = сюжет/заметки (свободное творчество мастера). Разделение ролей сохраняется 1-в-1.
- **Долговременная память = документы**: важные сюжетные решения записываются в заметки/листы/сцены (`game_hidden`, `game_visible`) — это память агента в БД, не сжимается. Чат-транскрипт — рабочая память (как Cursor: транскрипт сессии — кратковременная, файлы — долговременная).

### 2.11. Карта «умных фишек»: что даёт план, что в перспективе

**Про поиск правил (важно для «не выдумывать»):** сейчас `search_rules` — подстрочный LIKE по 8000 документам. Работает, но не понимает синонимы/перефразирования («урон огнём» не найдёт «fire damage»). Для глоссария правильный путь: FTS5 (быстрый ключевой поиск, встроен в SQLite, без зависимостей) → эмбеддинги (семантический: офлайн `@xenova/transformers` или онлайн OpenAI-эмбеддинги). Оба не трогают схему `Document` (отдельные индексы/таблицы) и подключаются внутрь `search_rules` как улучшение ранжирования.

### 2.12. Упрощение read-тулов до fs-стиля (опционально, Фаза 4+)

Текущие read-тулы уже ведут себя как файловая система: `read_document` принимает id ИЛИ путь (`resolveDocId`), `search_rules` = grep, `glossary_overview` / `get_brain` / `get_gm_notes` / `get_player_sheet` / `get_scene_state` = ls по «папкам». Буквальные `ls`/`cat` делать НЕ нужно: названия тулов несут смысл (search_rules = механика, get_gm_notes = секреты мастера), а гварды (`game_hidden` — мастеру, `game_visible` — по `playerId`, G36/G40) зашиты в код и описания тулов.

Реальный выигрыш — сконсолидировать read-side до трёх тулов (как read/grep/glob у Cursor):

- `list_documents(path?, type?)` — «дерево»: категории/типы/счётчики/топ названий (заменяет glossary_overview и списки get_brain/get_gm_notes/get_player_sheet/get_scene_state);
- `read_document(path)` — cat по виртуальному пути `/glossary/{type}/...`, `/brain/...`, `/hidden/...`, `/visible/{playerId}/...` (пути уже умеет);
- `search_documents(query, type?)` — grep по всем категориям (обобщение search_rules).

Плюсы: меньше тулов → меньше токенов на описания в промпте; модель знает семантику fs из коробки.
Условия: гварды секретности/прав переносятся в проверку путей тула; write-тулы остаются доменными (`create_document`/`update_document` с type/category). Не обязателен для ядра плана — рефактор Фазы 4+.

### 2.14. Сверка с реальными агентами (по официальной документации Claude Code)

**Подтверждено — наша архитектура совпадает с тем, как делает Claude Code:**

| Механизм Claude Code | Наш эквивалент |
|----------------------|----------------|
| Сессии = JSONL-транскрипт (`~/.claude/projects/<project>/<session>.jsonl`), `--resume` восстанавливает **полную историю, включая тул-колы и результаты** | `AgentTranscript` + `Message` + `buildTranscript` |
| `/compact` — замена истории структурированным саммари | `compressMessages` + `runChatSummarizer` → `ChatSummary` |
| Промпт-кэш при «resume as-is» (история пере-кэшируется и читается из кэша) | Фаза 4: стабильный префикс → контекст-кэш провайдера |
| Path-scoped правила `.claude/rules/` (грузится при чтении файла по маске) | `get_brain(topic)` + TOC в `read_document` |

**Нашли, чего не хватало (добавляем):**

1. **Auto memory — память агента о проекте, а не о переписке.** Claude Code хранит `~/.claude/projects/<project>/memory/`: `MEMORY.md` (индекс, первые 200 строк / 25 КБ — грузятся **каждую сессию**) + topic-файлы (читаются **по требованию**). Агент **сам пишет** туда выученное (команды, паттерны, инсайты). Переживает `/compact` — после сжатия `CLAUDE.md` и memory ре-инжектятся.
   → **У нас:** «документ памяти мастера» в `game_hidden` (или brain), который агент ведёт сам: индекс (в прелоаде) + секции по требованию; ре-инжекция после суммаризации. Это сильнее `ChatSummary`: память о проекте/игре, а не только о диалоге.
2. **Недавно прочитанные документы переживают сжатие.** При «resume from summary» Claude Code сохраняет в контексте «up to five recently read files».
   → **У нас:** после суммаризации держать в контексте последние N (5–10) прочитанных документов по `DocumentRead.readAt`.
3. **Дефер схем тулов (MCP tool search).** Claude Code грузит схемы тулов по требованию, чтобы не тратить контекст.
   → **У нас:** при 20+ тулах — отдавать модели только «горячий» набор (read/search/write), остальные — описанием. Низкий приоритет.
4. **Субагенты с отдельным контекстом** — подтверждено документацией: субагент читает файлы в своём окне, в основной возвращается только итог (~420 токенов вместо 6K). Это главный способ экономии на research. Подтверждает наш «долгосрок» как правильное направление.

## 3. Пофазный план работ

   - **Удаление сообщения** (user или итог): каскадно удаляем весь транскрипт раунда (`AgentTranscript where runId = message.runId`) — иначе контекст ссылается на удалённое сообщение. ChatSummary не пересчитывается (приемлемая цена — это сжатая память).
   - **Очистка чата**: удаляем все `Message` + все `AgentTranscript` сессии.
   - **Стоп**: `persistRun` пишет раунд со `status: "aborted"` (debug-только), следующий ход собирает контекст без него — «заново с нового сообщения» (как сейчас).

## 8. Метрики (как проверить «1-в-1 с Cursor»)

Инструменты замера уже есть: `traceAgent` (`AGENT_TRACE=1`), `logs/gm-game.log`.

- **Продолжение после рестарта (тест):** агент читает документ X → перезапуск → «что было в X?» → отвечает **из транскрипта без единого read-вызова**.
- **Контекст между раундами:** вопрос про данные, прочитанные 5 раундов назад → отвечает без перечитывания.
- **Чат чистый:** история содержит только итоговые сообщения (как сейчас); внутрянка в UI появляется ТОЛЬКО при `AGENT_DEBUG=1` и роли admin.
- **Стоп → новый ход (тест):** остановили раунд → отправили новое сообщение → агент отвечает «с чистого листа» от нового сообщения, aborted-внутренности в контексте отсутствуют (видны только в debug).
- **Удаление сообщения (тест):** удалили user-сообщение/ответ → следующий раунд не ссылается на удалённое и не ломает parts-формат транскрипта.
- **Среднее время ответа GM** (60–90 с): Фаза 1 → −50% (1 генерация вместо 2); Фаза 2 → первый токен < 10 с (внутренняя задержка — видна только в debug; игрокам итог показывается целиком, «облачко» как сейчас).
- **LLM-вызовов на ответ** (4–6): Фаза 1 → 1 генерация (внутри — шаги тулов).
- **Ошибок нет:** 10 раундов подряд без ошибок реконструкции parts-формата.
