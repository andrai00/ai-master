# Архитектурные принципы

## Ключевое решение: платформа не знает правил игры

Платформа **ничего** не знает про HP, ходы, раунды, инициативу, классы, расы, заклинания, бой, социальные конфликты. Всё это — зона нейронки через файлы.

Мы делаем универсальные примитивы. Нейронка решает логику.

---

## Граница: что пишем мы, что решает нейронка

### Мы (код-платформа)

| Примитив | Зачем |
|---|---|
| Файловое хранилище (.md, .yaml) | Всё игровое состояние |
| Чтение front-matter | Построение сайдбара, фильтрация по visibility/tags |
| Рендерер Markdown + скрытые маркеры + composite-документы | Отображение, сборка слоёв |
| Движок формул (детерминированный) | Вычисления вместо математики нейронкой |
| Чат: личный + общий | Общение |
| Инструменты для агентов | read, write, list, search, semantic_search, etc. |
| Drag-n-drop, кнопки бросков, слоты | Интерактивность |
| Индексация правил | Полнотекстовый + семантический поиск |
| SQLite | Пользователи, сессии, авторизация |

### Нейронка (логика)

- Структура глоссария и правил
- Секции, поля и формулы листов (всех типов)
- **Формат и смысл front-matter** — какие поля нужны под конкретную игру
- Игровая логика (проверки, сцены, бой, скрытые действия)
- Связи между документами
- Какие данные загружать в контекст в данный момент
- Какие файлы публичные, какие для памяти, какие скрытые

## Каноническая структура папок

Важно: **rules/ — плоская папка без вложенных директорий.** Секции и группировка строятся из front-matter, а не из структуры папок. Причина: один файл может относиться к нескольким категориям (например эльфы — и раса, и магия). Папки создают жёсткую иерархию, front-matter — гибкие теги.

```
данные-мастера/
  masters/
    <master-id>/
      sources/                ← сырые файлы от админа (PDF, DOC, TXT)
      rules/                  ← плоская папка: все .md файлы здесь
        _index.md             ← оглавление (генерится из front-matter)
        .index/               ← эмбеддинги для семантического поиска
        combat.md             ← type: rule, tags: [бой, инициатива]
        elf.md                ← type: race, tags: [эльф, ловкость]
        stealth.md            ← type: mechanic, tags: [скрытность]
        conditions.md         ← type: reference, tags: [состояния]
        ...                   ← никаких вложенных папок: races/, classes/, etc.
      skills/                 ← игро-специфичные скилы (тоже плоская)
      templates/              ← шаблоны листов (плоская)
      config.yaml             ← настройки мастера
      formulas.yaml           ← формулы

  sessions/
    <session-id>/
      characters/
        <player-id>/
          _base.md            ← ядро листа
          _composition.yaml   ← список слоёв
          data.yaml           ← companion: инвентарь, эффекты
      state/                  ← состояние игры
        scene.md
        effects.yaml
        summary.md
      logs/                   ← история сессии
        chat.md
        events.md
```

**Правило записи:**
- Builder пишет в `masters/<id>/rules/`, `templates/`, `skills/`, `config.yaml`, `formulas.yaml`
- Game Master читает `masters/<id>/` но НЕ меняет. Пишет только в `sessions/`
- Игроки НЕ пишут никуда — только через Game Master

## Метаданные файлов (front-matter + индекс)

Два уровня хранения метаданных:

### Источник истины — front-matter внутри .md

Каждый `.md` файл начинается с YAML между `---`. Это канонический источник.
Редактируется вместе с файлом, всегда синхронизирован с содержимым.

```yaml
---
title: "Боевые правила"
type: rule
summary: "Порядок хода, атака, урон, состояния."
visibility: public
tags: [бой, инициатива, атака]
---
```

### Поисковый кэш — `_index.yaml`

Автоматически генерируемый файл в корне `rules/`. Плоский массив всех
фронт-маттеров + поле `file` (имя файла). Пересобирается платформой
при любом изменении `.md` файла.

```yaml
# rules/_index.yaml
- file: combat.md
  title: "Боевые правила"
  type: rule
  visibility: public
  tags: [бой, инициатива]

- file: elf.md
  title: "Эльфы"
  type: race
  visibility: public
  tags: [эльф, ловкость, магия]

- file: gm-memory-001.md
  title: "Секретный сюжет"
  type: note
  visibility: hidden
  tags: [сюжет, босс]
```

**Как это работает:**
1. Агент создаёт/меняет `.md` файл — пишет front-matter внутри
2. Платформа видит изменение → парсит front-matter → обновляет строку в `_index.yaml`
3. Сайдбар рендерится одним чтением `_index.yaml` (мгновенно, без открытия `.md`)
4. Агент ищет файлы — читает `_index.yaml` → фильтрует по `tags`/`visibility` → открывает нужные `.md`
5. Удаление файла → удаление строки из индекса

**Почему не только front-matter:** открыть 50 `.md` файлов и распарсить YAML из каждого — медленно и дорого для LLM-контекста. `_index.yaml` — один файл, одна операция чтения, все метаданные сразу.

**Почему не только индекс:** индекс — производная. Редактировать его напрямую — риск рассинхрона. Источник правды в самом `.md` файле. Индекс пересобирается по факту изменений.

### Обязательные поля

| Поле | Назначение |
|---|---|
| `title` | Человеческое название (показывается в сайдбаре) |
| `type` | Тип: `rule`, `template`, `skill`, `character`, `scene`, `note`, `loot` |
| `summary` | 1-2 предложения. Агент читает ТОЛЬКО это перед открытием файла |
| `visibility` | `public` — всем игрокам; `private` — конкретному; `hidden` — только AI |
| `tags` | Гибкие теги для группировки и поиска |

### Опциональные поля (нейронка добавляет под игру)

```yaml
section: "Шпаргалки"  # секция в сайдбаре (без неё — авто по type)
order: 1              # сортировка
owner: garret          # для visibility: private
status: active         # draft | active | archived
keywords: [бой, КД]
```

Поля не фиксированы. D&D может добавить `level: 3`, Vampire — `clan: toreador`,
PbtA — `move_trigger: "Когда ты..."`. Нейронка сама решает структуру под игру.

### Связи между файлами

Внутри `.md` файлов связи через wiki-ссылки:

```md
Эльфы получают бонус к [[stealth|скрытности]] и [[perception|восприятию]].
Подробнее в разделе [[combat|боевые правила]].
```

`[[имя-файла]]` или `[[имя-файла|текст ссылки]]`. Рендерер превращает в кликабельные ссылки. Агент идёт по ним при необходимости.

```
данные-мастера/
  masters/
    <master-id>/
      sources/                ← сырые файлы от админа (PDF, DOC, TXT)
      rules/                  ← структурированные правила (создаёт Builder, НЕ менять)
        _index.md             ← оглавление глоссария (читается всегда)
        .index/               ← эмбеддинги для семантического поиска
        glossary.md           ← терминология
        races/                ← папки и файлы как решит нейронка
        classes/
        items/
        mechanics/
        ...
      skills/                 ← игро-специфичные скилы (создаёт Builder)
        character-creation.md
        combat-resolution.md
        ...
      templates/              ← шаблоны листов (создаёт Builder, НЕ менять)
        character-sheet.template.md
        shared-sheet.template.md
      config.yaml             ← настройки мастера
      formulas.yaml           ← формулы (если вынесены отдельно)

  sessions/
    <session-id>/
      characters/
        <player-id>/
          _base.md            ← ядро листа (имя, текущие значения)
          _composition.yaml   ← список слоёв (раса, класс, уровень...)
          data.yaml           ← companion: инвентарь, эффекты, связи
      state/                  ← состояние игры
        scene.md              ← текущая сцена
        effects.yaml          ← активные эффекты
        summary.md            ← авто-саммари (контекст)
      logs/                   ← история сессии
        chat.md               ← логи чата
        events.md             ← игровые события
```

**Правило записи:**
- Builder пишет в `masters/<id>/rules/`, `templates/`, `skills/`, `config.yaml`, `formulas.yaml`
- Game Master читает `masters/<id>/` но НЕ меняет. Пишет только в `sessions/`
- Игроки НЕ пишут никуда — только через Game Master

## Три слоя в документе (как данные живут в файле)

Один "документ" (лист персонажа) состоит из трёх слоёв, и только один игрок видит:

### Слой 1: Тело .md (видимое игроку)

```md
# Гаррет
**HP:** 38 / 45
**Оружие:** Короткий меч (1d6 piercing)
```

Рендерер подставил данные из слоёв 2 и 3. Игрок видит только это.

### Слой 2: Front-matter (скрытое, простые значения)

```yaml
---
hp_current: 38
hp_max: 45
equipped_weapon: short_sword
---
```

Скалярные значения. Игроку не показываются. Рендерер читает и использует для подстановки и формул.

### Слой 3: Companion-файл (скрытое, сложные структуры)

`data.yaml` рядом с `.md`:

```yaml
inventory:
  - id: sword_01
    name: Короткий меч
    equipped: right_hand
    stats: { damage: "1d6", type: piercing }
    weight: 2
  - id: potion_03
    name: Зелье лечения
    equipped: false
    weight: 0.5

active_effects:
  - id: bless_01
    source: Заклинание жреца
    modifier: { attack: +2 }
    duration: 3_rounds
```

Инвентарь, эффекты, связи, история — всё что не лезет во front-matter.

## Composite-документы (сборка листа из слоёв)

Игрок видит ОДИН лист. Внутри это сборка:

```yaml
# _composition.yaml
layers:
  - race: elf
  - class: rogue
  - level: 3
  - template: character-sheet.template.md
```

Каждый слой — ссылка на шаблон из `masters/<id>/templates/` или на «дельта-слой» (частичное переопределение).

**Как работает сборка:**
1. Рендерер читает `_composition.yaml`
2. Собирает слои в порядке приоритета (первый — базовый, дальше — наложения)
3. Обсчитывает формулы (учитывая все слои)
4. Показывает итоговый лист

**Почему это важно:**
- Маг получает заклинания → добавляется секция spellbook (не вся структура меняется, а добавляется слой)
- Псионик получает дисциплины → добавляется слой psionics с другой структурой
- Игрок получает уровень → добавляется слой уровня с бонусами
- Временный эффект «благословение» → слой на 3 хода

Нейронка меняет структуру через слои, не переписывая всё.

## Как composite-документ соотносится с тремя слоями данных

Composite-документ — это механизм **структурной композиции** (как собрать лист из кусков).

Три слоя данных — это механизм **разделения отображения и данных внутри одного куска**.

Они ортогональны:

| | Слой composite | Три слоя данных внутри |
|---|---|---|
| `_composition.yaml` | Указывает какие куски собрать | Нет (это мета-файл сборки) |
| Шаблон `.template.md` | Один из кусков | Есть: тело (разметка), front-matter (параметры по умолчанию) |
| Дельта-слой (уровень) | Один из кусков | Есть: тело (что добавилось), front-matter (что изменилось) |
| `data.yaml` (companion) | Общий для всего листа | Слой 3 (сложные данные) |
| `_base.md` | Ядро листа | Все три слоя |

То есть composite отвечает на вопрос «из каких кусков состоит лист», а три слоя — на вопрос «где в каждом куске данные, а где отображение».

## Скрытые маркеры в .md

Нейронка может использовать HTML-комментарии для мета-данных прямо в теле:

```md
# Боевая сцена: Таверна

<!-- meta:initiative:["гаррет","гоблин","эльф"] -->
<!-- meta:current_turn:0 -->
<!-- meta:round:3 -->

Гаррет стоит у стойки. Гоблин за столом.
```

Формат маркеров **не фиксирован** — нейронка сама решает что ей нужно. Рендерер парсит их, скрывает от игрока и может использовать для отображения (например, показать счётчик раунда).

## Про базу данных

**Не нужна** для игрового контента. Файлы — гибче, нейронка работает с ними нативно, никакая схема БД не опишет «любую RPG».

**Нужна SQLite** (`better-sqlite3`, один файл, без сервера) для:

- Пользователи, пароли (bcrypt-хеши)
- Сессии и токены
- Ссылки на дампы/конфиги мастеров
- (возможно) версионные снапшоты для миграций

Нейронка в БД напрямую не пишет. Только файлы.

## Движок формул (принцип)

- Нейронка **задаёт** формулы (Builder), нейронка **указывает** какие данные подставить (Game Master)
- Вычисляет **код** детерминированно
- Формулы хранятся как данные, могут меняться (и во время игры — эффекты)
- Поддерживают: переменные, ссылки на поля, броски кубов, условия
- Автоматический пересчёт зависимостей: изменили силу → обновились все формулы которые на неё ссылаются

## Итоговый список того что мы пишем кодом

1. Файловое хранилище (с версионированием под вопросом — `07-open-questions.md`)
2. Рендерер Markdown: скрытые маркеры, сборка composite-документов, подстановка данных
3. Чат: личный/общий, стриминг, кнопки бросков, команды
4. Drag-n-drop: слоты инвентаря/экипировки
5. Движок формул: парсинг выражений, вычисление, граф зависимостей
6. Инструменты для агентов: read, write, list, search (полнотекстовый), semantic_search, send_chat
7. Индексация правил: индекс от Builder'а (полнотекстовый + эмбеддинги)
8. SQLite: пользователи, сессии, авторизация
9. Парсеры документов: PDF, DOCX, TXT
10. Сервер: HTTP + SSE/WS

Всё остальное — зона нейронки.
