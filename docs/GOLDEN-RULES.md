# Golden Rules — незыблемые законы проекта

> Нарушение любого из этих правил = баг или архитектурный дефект.
> Правила нумеруются (G1..G43) для ссылок: «нарушено G8».

---

## G1 — Server Actions по умолчанию

**Суть:** все мутации и запросы данных — через Server Actions. API Routes — только когда Server Action не подходит.

**Когда API Route:**
- Загрузка файлов >1MB body
- Webhook-обработчики
- Стриминг больших данных
- Когда нужен свой `bodySizeLimit`

**Нарушение:** создание `route.ts` для обычного CRUD.

---

## G2 — Синглтон через globalThis

**Суть:** НИКОГДА `let` на уровне модуля для кэша. Только `globalThis`-паттерн:

```ts
const globalX = globalThis as unknown as {
  instance: Thing | undefined;
  promise: Promise<Thing> | undefined;
};
export async function getThing(): Promise<Thing> {
  if (globalX.instance) return globalX.instance;
  if (!globalX.promise) globalX.promise = createThing();
  globalX.instance = await globalX.promise;
  return globalX.instance;
}
```

**Почему:** при горячей перезагрузке Next.js `let` теряется.

## G3 — Цвета только через CSS-переменные

**Суть:** никаких `#333`, `#d4d4d4`, `#1a1a1a`, `rgb(...)`. Только `var(--border)`, `var(--bg-surface)`, `var(--text-primary)`.

**Нарушение:** любой хардкод цвета.

## G4 — Все статические тексты через i18n

**Суть:** `title`, `placeholder`, `Tooltip`, `Modal`, `notification` — через `t()`. Исключение: динамические данные из БД.

```tsx
const { t } = useTranslation();
t("auth.login")
```

**Нарушение:** русский или английский текст в `title="..."` или `placeholder="..."`.

**Нарушение:** `pagination={false}`.

## G7 — Деструктивные действия с подтверждением

**Суть:** `Popconfirm` для удаления, `modal.confirm` из `App.useApp()` для выхода/смены.

**Нарушение:** удаление без подтверждения.

## G8 — Danger/красный только для удаления

**Суть:** `type="primary" danger` — только для необратимых действий (удаление, сброс). Выход, возврат, закрытие — обычные кнопки.

**Нарушение:** красная кнопка «Cancel» или «Back».

## G9 — modal.confirm с mask: { closable: true }

**Суть:** `modal.confirm` из `App.useApp()` не закрывается по клику на фон по умолчанию. Всегда `mask: { closable: true }`.

**Нарушение:** модалка, которую нельзя закрыть кликом мимо.

## G10 — React Query только через хуки

**Суть:** компонент не использует `useQuery`/`useMutation` напрямую. Только через хуки в `src/shared/api/{domain}/use-*.ts`.

```tsx
// В компоненте:
import { useListGames } from "@/src/shared/api/admin/use-list-games";
const { data: games } = useListGames();
```

**Нарушение:** `useQuery` напрямую в компоненте.

## G11 — useMutation на все мутации

**Суть:** create, update, delete — всегда через `useMutation` + `queryClient.invalidateQueries`.

**Нарушение:** прямой вызов server action без `useMutation`.

## G13 — Режимы с последствиями — кнопка + подтверждение, не Switch

**Нарушение:** Switch для переключения development/game mode.

**Суть:** `updatedAt DateTime @default(now()) @updatedAt`. Без `@default(now())` ломает `db push`.

**Нарушение:** `updatedAt DateTime @updatedAt` без `@default(now())`.

**Нарушение:** доступ к dev-страницам в game-режиме.

## G16 — Активная страница в сайдбаре через usePathname

**Суть:** `const isActive = (route: string) => pathname.startsWith(route)`. Активный стиль: `background: var(--bg-active)`.

**Нарушение:** новый пункт меню без подсветки активной страницы.

## G17 — Схема БД синхронизирована до перезапуска dev-сервера

**Суть:** `npx prisma db push && npx prisma generate` до тестирования. Миграции-файлы не используются — схема применяется через `db push` (иначе старый клиент в `globalThis` = баги).

**Нарушение:** изменение схемы без `db push` + `generate`.

## G18 — SSE-push для глобальных событий

**Суть:** смена игры, режима, потеря доступа — SSE-push всем клиентам, не полагаться на опрос.

**Нарушение:** клиент опрашивает сервер каждые N секунд вместо SSE.

---

## G19 — Builder Agent: fire-and-forget + SSE

**Суть:** server action сохраняет сообщение → запускает `runBuilderAgent()` без await → сразу возвращает `{ success: true }`. Прогресс и ответ — через SSE.

**Нарушение:** `await runBuilderAgent()` в server action (блокирует HTTP-запрос на 2 минуты).

---

## G20 — Коммиты только по явной просьбе

**Суть:** агент не коммитит самостоятельно. Только когда пользователь явно скажет «закоммить» или «сделай коммит».

**Нарушение:** авто-коммит после завершения задачи.

---

## G21 — AI-обработка только через очередь

**Суть:** `runBuilderAgent()` никогда не вызывается напрямую из server action. Только через `enqueueBuilderJob()` → `better-queue` (max 3 concurrent). Очередь персистентна через `BuilderJob` table, восстанавливается при рестарте.

**Почему:** без очереди 10+ одновременных `generateText()` забивают event loop, SQLite и память.

**Нарушение:** прямой вызов `runBuilderAgent()` в обход `enqueueBuilderJob()`.

---

## G22 — Импортированный контент полным текстом, не чанками

**Суть:** `.md` файлы из архива импортируются в `Document.content` одной записью на документ. Никаких чанков, никакого постраничного хранения.

**Почему:** запись чанков в БД = множественный SQLite write lock → блокирует страницы, server actions, SSE.

**Нарушение:** разбиение одного документа на множество записей в таблице.

---

## G23 — Импорт файлов через архив, не чанковое чтение

**Суть:** файлы загружаются как `.zip` архив с `.md` файлами (или одиночный `.md`). AI НЕ читает содержимое каждого файла — вместо этого `explore_archive()` показывает дерево папок с количеством файлов. AI определяет типы по структуре папок (не по контенту), затем `bulk_import_to_glossary` создаёт все Document'ы одной серверной операцией. Документы получают названия с путём: `classes/87-barbarian`, `rules/inventory/96-arms`. Все тулзы документов принимают и UUID и путь.

**Алгоритм:**
1. `explore_archive()` → дерево папок + **плоский список `folders`** (каждая папка с полным путём и кол-вом файлов) + sample-имена
2. AI определяет тип для каждой папки ПО СМЫСЛУ содержимого (не копируя имя папки): `/bestiary/` → "monster", `/spells/` → "spell", `/homebrew/spells/` → "spell" (homebrew/multiverse/rules — источники, НЕ типы)
3. `bulk_import_to_glossary(typeMap)` — маппинг `{ папка: тип }`, совпадение **по префиксу, longest wins**: `{ "/rules": "rule", "/rules/bestiary": "monster" }` — всё под `/rules` как rule, кроме `/rules/bestiary` как monster
4. Файлы, не попавшие ни под один префикс, возвращаются в `skipped` (до 20) — модель видит и дополняет typeMap
5. После импорта UploadedFile записи удалены, работает только с Document

**Почему:** чанковое чтение 8000 файлов требовало бы десятки тысяч AI-шагов. Определение типов по структуре папок + серверный пакетный `createMany`/`updateMany` — O(1) AI-шагов + ~20 SQL-запросов вместо ~17 000.

**Нарушение:** чтение содержимого файлов при импорте архива (read_file в цикле); цикл `findFirst`+`create` по файлам (см. G32).

---

## G24 — SSE-push для всех мутаций чата между клиентами

**Суть:** удаление/создание сообщений, затрагивающие других админов — всегда через `broadcastGameEvent()` + SSE-push. Не полагаться на React Query (он per-client).

**Почему:** React Query cache — per-browser. Invalidate на админе A не триггерит refetch на админе B. Только SSE гарантирует синхронизацию.

**Нарушение:** мутация чата без `broadcastGameEvent`.

---

## G25 — Все страницы используют единый `<PageHeader>` компонент

**Суть:** каждая страница приложения рендерит `<PageHeader title="..." actions={...} />`. Запрещены inline-стили для заголовков, отдельные `h2`, самописные header-div'ы. Компонент находится в `src/shared/ui/page-header.tsx`.

**Почему:** без единого компонента дизайн шапок расходится (разные font-size, padding, border). Мобильная кнопка меню дублируется или отсутствует. Любое изменение шапки требует правок во всех страницах.

**Нарушение:** `<h2 style={{ fontSize: 16 }}>` или `<div className="pageHeader">` вместо `<PageHeader>`.

---

## G26 — Real-time только через EventEmitter push, никакого polling

**Суть:** SSE-эндпоинты не опрашивают буфер через `setTimeout`. Вместо этого используют `EventEmitter` + подписку (`onStep`, `onGameEvent`). Источник данных (step-tracker, game-events) пушит события подписчикам мгновенно.

**Почему:** `setTimeout(poll, 300)` создаёт задержку 0-300ms, ломает синхронизацию между клиентами (отправитель получает событие позже чем другие). EventEmitter доставляет мгновенно — все клиенты получают событие в одной итерации event loop.

**Нарушение:** `setTimeout` в SSE-роуте для опроса источника данных.

---

## G27 — DB-update перед broadcast всегда с `await`

**Суть:** если действие меняет БД и затем шлёт SSE-событие другим клиентам через `broadcastGameEvent` — БД-запись должна быть завершена ДО броадкаста. `prisma.x.update().catch()` без `await` создаёт гонку: broadcast уходит до коммита, рефетч возвращает старые данные.

**Почему:** без `await` клиент получает SSE-событие, рефетчит запрос, но БД ещё не обновлена → видит старое значение. Пользователь видит рассинхрон между баблом и данными.

**Нарушение:** `prisma.document.update(...).catch(() => {})` без `await` перед `broadcastGameEvent`.

---

## G28 — Набор тулзов агента разделён по доменам и режимам

**Суть:** инструменты агентов группируются по логическим доменам, и модели передаётся соответствующий набор:
- **GM** (игровой/личный чат): `search_rules` (глоссарий), `glossary_overview` (карта типов глоссария), `get_brain` (мозг), `get_gm_notes` / `get_scene_state` (игровая память), `get_player_sheet` (данные игрока), `get_players`, `resolve_glossary_link`.
- **Builder**: BRAIN mode → глоссарий + мозг (`search_rules`, `glossary_overview`, `get_brain`, файловый импорт); MEMORY mode → игровая память и данные игроков (`get_gm_notes`, `get_scene_state`, `get_player_sheet`), как в игровом чате.

Внутри режима подрежимы (IMPORT / CHAT у билдера) регулируются через system prompt, а не через скрытие тулзов. Все инструменты документов принимают и UUID и путь. Агент сам решает, когда использовать импорт-тулзы, на основе инструкций в промпте.

Агенты работают в **единый агентный цикл** (single loop): одна генерация `streamText` с полным набором тулов. Модель сама решает: изучить → действовать → ответить. Двухфазная схема Plan → Execute и `study-summary` УДАЛЕНЫ (см. G30, G40).

**Почему:** единый `search_documents` заставлял модель угадывать, где что искать, и приводил к сбоям (лист игрока тонул за глоссарием, GM не находил данные игрока). Разделение по доменам даёт модели явные «скиллы». Типизация `generateText<typeof tools>` решается явным типом `ToolSet` на `getTools()`.

## G29 — Результаты значимых бросков сохраняются в game_hidden

**Суть:** после `confirm_rolls` роллы помечаются `consumed=true` и исчезают из видимости AI. Если результат броска важен для дальнейшей игры (инициатива, хиты, спасброски, урон по врагу) — AI обязан сохранить его через `write_note` или `update_document` в `game_hidden` ДО вызова `confirm_rolls`.

**Почему:** consumed-роллы невидимы для AI в будущих итерациях. Без сохранения — полная потеря контекста. Для сиюминутных проверок (кинул→ответил→забыл) — не требуется.

**Реализация:**
1. AI вызывает `get_rolls` → видит результаты
2. AI использует результаты в ответе игроку
3. AI вызывает `write_note("Инициатива боя", "Гаррет: 18, Элен: 14, Гоблин: 12")` — сохраняет в game_hidden
4. Только потом `confirm_rolls` — роллы consumed

**Нарушение:** `confirm_rolls` до сохранения важных результатов → потеря данных.

---

## G30 — Ответ агента: единый агентный цикл, доставка текстом

**Суть:** агенты (GM общий/личный, Builder) работают в **один цикл** — одна генерация `streamText` с полным набором тулов (`stopWhen: isLoopFinished() || isStepCount(100)`). Модель сама решает: изучить (read-тулы) → действовать (write/roll-тулы) → написать финальный ответ. Двухфазный Plan → Execute удалён.

Доставка: `result.text` (эмитится шаг `final`). Если текст пуст после tool-вызовов — **один ретрай БЕЗ тулов** с принудительным «ответь по результатам, которые уже получил» (`FORCE_ANSWER_PROMPT`); ретрай получает результаты текущего раунда через `stepsToModelMessages` (обёртка `{type:"json",value}` обязательна — иначе SDK валидирует output как JSONValue и падает). Затем fallback-сообщение.

**Гейт «пустой вызов»:** если нет новых сообщений и нет завершённых необработанных роллов — LLM не вызывается вовсе, сразу `done` (раньше был короткий «idle»-вызов).

**Источники фактов:** каждый read-тул помечает результат полем `source` (`glossary`, `game_visible`, `game_hidden`, `brain`, `rolls`, `players`, `chat_summary`). Модель обязана учитывать источник: факты из `game_hidden`/`brain` не раскрывать игрокам.

**Почему:** единый цикл — ровно как у Cursor/Claude Code: 1 генерация вместо 2, нет двойных задержек. «Модель обещала бросок, но не вызвала тул» решается промптом + гарантированным retry по результатам раунда.

**Реализация:** `streamText` + полный набор тулов; весь ход раунда (тул-колы + результаты) пишется в `AgentTranscript` (см. G40). Ретрай пустого ответа — только один, без тулов. Рекурсивный batch не нужен: серверные экшены отправки блокируют новые сообщения во время обработки (`isProcessing`).

## G31 — Мозг прелоажен в контекст, глоссарий — только по необходимости

**Суть:** мозг (инструкции мастера) прелоадится в системный промт автоматически (`## Brain (preloaded)` — index + список секций с типами), поэтому `get_brain(topic)` нужен только для чтения конкретной секции целиком. Глоссарий НЕ прелоадится и НЕ ищется «на всякий случай»: `search_rules` — только когда реально нужна конкретная механика/цифра/предмет/класс и мозг/память не дали ответа.

**Порядок изучения:**
1. Мозг прелоажен в контексте — читать оттуда
2. Память мастера (`hidden/memory/*`) и данные (`get_gm_notes`, `get_scene_state`, `get_player_sheet`, `get_chat_summary`) — тоже прелоажены
3. `glossary_overview` — один раз, чтобы понять структуру глоссария (типы + количество)
4. `search_rules(query, type?)` — только по необходимости (редкое правило, предмет, полный список, homebrew)

**Реализация:** `buildBrainContext()` в раннерах собирает мозг в динамическую часть промта; `glossary_overview` — read-only тул с картой типов; `search_rules` принимает `type` (фильтр) и `limit`, возвращает `{ total, returned, docs }`.

**Нарушение:** вызов `search_rules` без нужды, чтение всего глоссария, повторный `get_brain` для уже прелоаженного.

---

## G32 — Массовые операции с БД — пакетные, никогда цикл по записям

**Суть:** любые операции с тысячами записей (импорт, обновление, сканирование) выполняются пакетно: один `findMany` существующих + `createMany`/`updateMany` чанками. НЕЛЬЗЯ цикл `findFirst` + `create`/`update` на каждую запись — тысячи последовательных SQLite-запросов держат write-lock на минуты и замораживают весь Next.js.

**Пример (bulk_import):** вместо `for (f of files) { findFirst; create/update; }` (~17 000 запросов при 8592 файлах) — один `findMany` title + `createMany` чанками по 500 + чанкованные `update` (~20 запросов).

**Нарушение:** цикл по записям в server action / туле агента.

---

## G33 — SQLite в WAL-режиме

**Суть:** `PRAGMA journal_mode=WAL` + `busy_timeout=5000` при инициализации Prisma (`prisma.ts`). Без WAL одна массовая запись агента берёт эксклюзивный lock на весь файл БД — сайт (чаты, страницы, SSE) ждёт очереди и «висит». WAL позволяет читателям работать параллельно с писателем.

**Нарушение:** `journal_mode=delete` (по умолчанию) — сайт замирает во время импорта/массовых записей.

---

## G34 — Во время обдумывания мастера нельзя: отправлять сообщения, бросать кости

**Суть:** пока GM/Builder обрабатывает (`isProcessing(sessionId)`), серверные экшены **отклоняют**:
- отправку сообщений (send-game / send-personal / send-builder) → `chat.processingBlocked`
- выполнение бросков (`executeRollAction`) → `chat.processingBlocked`

Клиент показывает уведомление. Это заменяет рекурсивный batch: новые сообщения во время генерации просто не могут появиться.

**Реализация:** guard в `gm-runner.ts` (`isProcessing`) / `builder-runner.ts`, проверка в начале экшенов. Броски блокируются в обоих чатах (игровой и личный).

## G35 — Мета-вопросы к мастеру — ответ вне роли НПС

**Суть:** если игрок пишет «вопрос к тебе мастер», «вопрос мастеру», «вне игры», «мета», «оффтоп» или спрашивает о мире/правилах/сеттинге напрямую — GM отвечает как рассказчик (кратко, фактами, вне сцены), а НЕ вкладывает ответ в уста НПС. В роли НПС — только когда игрок обращается к НПС в сцене.

**Почему:** иначе GM отыгрывает старосту, который «знает» про гильдии, вместо ответа о мире.

## G36 — get_rolls только для старых/спорных бросков

## G37 — Игроки открывают glossary по ссылкам из чата

## G39 — Диагностика агентов — AGENT_TRACE

**Суть:** для анализа промтов/действий нейронки при `AGENT_TRACE=1` пишется таблица `TraceEvent`: каждый промт (system + messages), каждый тул-вызов (имя + аргументы), финальный ответ, `finishReason`, ошибки, тайминги — с тегом чата/фазы/sessionId. Без флага ничего не пишется. После анализа флаг убрать и дропнуть таблицу.

**Реализация:** `src/shared/lib/agents/trace.ts` → `traceAgent({ chat, sessionId, phase, stepIndex, toolName, args, result, prompt, error, finishReason, elapsedMs })`. Лимиты: args ≤2К, result ≤4К, prompt ≤20К. Фазы — `exec` / `retry` (Plan/exec/idle больше нет).

**Аргументы тулов — `input`, не `args`:** AI SDK v7 кладёт аргументы tool call'а в поле `call.input` (а `call.args` отсутствует). В `onStepFinish`/`makeStepLogger` писать `JSON.stringify(call.input ?? call.args ?? {})` — иначе в трейсе будут пустые `args: {}`.

**Тайминги:** `elapsedMs` — реальный замер `performance.now()` вокруг генерации (exec/retry). Без замера всегда 0 и бесполезен.

## G40 — Транскрипт раундов (`AgentTranscript`) вместо study-summary

**Суть:** каждый раунд целиком (тул-колы с аргументами, результаты, финальный текст, статус) персистентно пишется в таблицу `AgentTranscript`. При следующем ходе транскрипт реконструируется в контекст (`buildTranscript`), поэтому модель видит, что она уже прочитала/сделала, и НЕ перечитывает. `study-summary.ts` УДАЛЁН: в single loop перечитывание не проблема — всё изученное уже в контексте одной генерации.

**Почему:** двухфазная схема порождала дубли чтения (до 6 на батч) и лишние LLM-вызовы (30–100 сек). Транскрипт решает это структурно: вся история изучения уже в контексте, плюс переживает рестарт.

**Реализация:** `src/shared/lib/agents/transcript.ts` → `persistRun` (атомарно: транскрипт раунда + журнал изученных документов `DocumentRead`) и `buildTranscript` (реконструкция `ModelMessage[]` в parts-формате ai@7; tool-result — `role: "tool"` c `output: { type:"json", value }`). Старые волны сжимаются фоновым `chat-summarizer.ts` в `ChatSummary`. Удаление сообщения каскадно удаляет транскрипт раунда (`cascadeDeleteMessageRun`) — откат = память пропадает, агент ищет заново.

**Исключение:** модель может дочитать конкретный документ через `read_document`, если нужного нет в контексте. Для вопросов о правилах до фолбэка на общие знания обязателен `search_rules` в этом ходе.

## G41 — read_document: GM капит чтение, Builder читает полностью

**Суть:** разные лимиты чтения у GM и Builder:
- **GM** (`gm-read-document.tool.ts`): `Math.min(args.limit ?? 3000, 8000)` — защищает контекст от вливания больших секций (механики 25 КБ) целиком. GM не создаёт/не разбивает документы — ему хватает фрагмента + `hasMore`/`offset`.
- **Builder** (`read-document.tool.ts`): полное чтение при отсутствии `offset`/`limit` — возвращает весь `doc.content` одним вызовом. Билдер создаёт, редактирует и разбивает документы — ему нужен полный текст.

**Почему:** кап 8000 на билдере заставлял модель дробить 25 КБ документ на 4 части (`offset: 0/8000/16000/24000`) — 4 LLM-вызова вместо 1, билдер замедлялся в 3–4 раза. Кап полезен GM (не дробит, мелкие документы) и вреден билдеру.

**Нарушение:** единый кап для обоих тулов; билдер, читающий документ чанками по 8000.

## G42 — Структура мозгов: секции ≤7КБ, индекс 3–5КБ, одна тема — в одном месте

**Суть:** brain-документы создаются по правилам, чтобы мозг не раздувал контекст каждого вызова:
1. **Секция ≤ ~6–7 КБ.** Тема больше лимита разбивается на под-секции `rules/<подтема>` (`rules/combat`, `rules/rest_death`, `rules/magic`, `rules/npc_relations`). GM читает нужный фрагмент через `get_brain(topic)`, а не весь файл на 25 КБ.
2. **`_index` — только навигация + политика (3–5 КБ).** Роутер «тип запроса → секция/глоссарий», порядок создания персонажа, маршрутизация сообщений, краткая политика. БЕЗ сводок механик, дублирующих секции.
3. **Одна тема — одно место.** Дубли между `_index` и секциями запрещены: полный текст живёт в одной секции, остальное — ссылки `[[path]]`. Дубли путают GM и раздувают контекст.
4. **После разбивки** — обновить роутер в `_index` и перенаправить старые wiki-ссылки (`scan_wiki_links`/`replace_wiki_links`).

**Реализация:** правила записаны в гайд билдера (`get_builder_guide.tool.ts`, topic `brain` → «Brain structure rules»). Билдер создаёт новые мозги сразу компактными; старые мозги правятся через билдер-чат по этим правилам.

**Нарушение:** создание секции 25 КБ; индекс со сводками механик; дублирование одной темы в индексе и секции.

## G43 — Активная игра — источник истины для документов агента

**Суть:** `read_document`/`create_document`/`update_document`/`get_brain` работают с **активной** игрой (`ActiveGame.currentMasterId`). Перед задачей билдеру/мастеру по мозгам — проверить, какая игра активна (`getActiveGame()`), и передавать ID документов именно из неё. В БД могут лежать несколько копий одного индекса/секции (по одной на мастер-игру) — правка «не той» копии бесполезна.

**Почему:** в сессии 19.08.2026 билдер получил ID индекса из игры «DnD test 2», а активной была «dnd test 3» — он обновил устаревший дубль, а активный индекс остался со старыми битыми ссылками (19 шт).

**Нарушение:** передача агенту ID документов без проверки активной игры; правка документов неактивного мастера.

## G44 — Новая архитектура агентов: пути, транскрипт, память, debug

Сводка изменений рефакторинга (2026-08) — единая точка правды для новых правил:

1. **Уникальные пути документов.** Каждый документ имеет `path` с префиксом категории (`glossary/...`, `brain/...`, `hidden/...`, `visible/<playerId>/...`), уникальный в рамках игры (`[masterId, path]`). Ссылки — только `[[path|label]]`, id модели НЕ показываются. Резолвер (`resolveDocumentByPath`) поддерживает архивные ссылки без префикса (авто-`glossary/`). Переименование — только тулом `rename_document` (каскад обновляет ВСЕ ссылки обеих форм по точным границам токена; `пример_ссылки_2` не затрагивается). `create_document` отклоняет занятый путь — перезапись невозможна. В сохранении JSON id не пишутся (легаси нет).
2. **Память = транскрипт + документы.** `AgentTranscript` хранит каждый раунд целиком и реконструируется в контекст (G40). Долговременная память — документы: `hidden/memory/*` (структура задаётся Builder в brain-политике `memory_management`), `hidden/notes/*`, `visible/*`. Прелоад: мозг + память мастера.
3. **Память мастера.** Секции `hidden/memory/*` по ролевке; границы: `memory` = долговременное, `notes` = текущая сцена, `visible` = игроку. Авто-архив старых сцен при разрастании.
4. **Debug.** `AGENT_DEBUG=1` (admin) — в чате строки вызовов тулов (иконка + имя + аргументы) в реальном времени и после ответа; `AGENT_TRACE=1` — таблица `TraceEvent` (G39). Файловые логи (`logs/*.log`) удалены.
5. **Санитизация output'ов тулов.** `wrapToolSet` прогоняет результат каждого тула через JSON (Date → ISO-строка) — иначе ai@7 валидирует output как JSONValue и падает с «No output generated».
6. **Поиск.** Единый ранкинг для `search_rules` и страницы документов: точное название → префикс → вхождение → summary → содержимое; новые выше. Промпт: для вопросов о правилах — мозг/`search_rules` в этом ходе, фолбэк на общие знания только после поиска.
