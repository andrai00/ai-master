# Концепция

## Общая идея

Универсальный ИИ-мастер, которого админ настраивает под любую настольную ролевую игру. Два агента: **Builder** помогает админу создать/настроить мастера, **Game Master** ведёт игру с игроками.

Интерфейс — подобие Notion/Obsidian: слева сайдбар (чат-навигация + контекстные секции), страницы с отдельными URL вместо вкладок. Данные в Prisma + SQLite.

Проект не привязан к D&D. Все примеры с D&D — просто иллюстрации; система должна одинаково хорошо работать с Fate, Vampire, Call of Cthulhu, PbtA, самописными системами и т.д.

## Два режима: разработка и игра

У каждого мастера (игры) есть два взаимоисключающих режима. Они не пересекаются — в каждый момент времени мастер находится либо в одном, либо в другом.

### Режим разработки (Development mode)

Админ + Builder. Правила и структура игры создаются и дорабатываются. Игроки не подключены, игровые сессии не идут.

**Что происходит:**
- Builder изучает загруженные правила, задаёт уточняющие вопросы
- Строит глоссарий и мозг (правила для ИИ)
- Создаёт шаблоны, формулы, скилы
- Админ корректирует, правит, перестраивает

**Что можно менять:** глоссарий, мозг (AI rules) — всё что составляет правила игры.

### Режим игры (Game mode)

Игроки + Game Master. Правила зафиксированы, идёт живая игра.

**Что происходит:**
- Game Master ведёт игру, используя структуру созданную Builder'ом
- Игроки общаются в общем и личных чатах
- Пишутся игровые данные: заметки мастера, планы, листы персонажей, логи

**Что можно менять:** только игровые данные (скрытые заметки ИИ и видимые игрокам листы/состояния).

**Что нельзя менять:** глоссарий и мозг (правила). Они read-only на всё время игры.

### Переключение режимов и миграции

Админ в любой момент может переключить мастера в режим разработки, чтобы доработать правила:

1. **Админ переключает в Development mode** — игра приостанавливается
2. **Builder вносит изменения** в глоссарий/мозг по указаниям админа
3. **Builder формирует сводку изменений** — что именно поменялось, какие механики затронуты
4. **Админ переключает обратно в Game mode**
5. **Game Master читает сводку изменений** и **сам решает**, нужно ли обновить данные игроков (листы персонажей, состояния, эффекты)
6. Если нужно — Game Master вносит изменения через инструменты обновления листов

Важно: **игроки не теряют данные**. Game Master адаптирует существующие листы под новые правила, а не пересоздаёт с нуля.

## Категории данных

Все данные хранятся в БД в формате Markdown (колонка `content` в таблице `Document`). Не в файлах — в БД, с метаданными в соседних колонках для фильтрации и поиска. Нейронка сама решает структуру внутри каждой категории, мы даём только разделение на 4 типа:

### 1. Глоссарий (категория `glossary`)

Исходный материал, загруженный админом. Хранится почти 1-в-1 как загрузили. Может меняться по запросу админа, но по сути это справочник к которому ИИ обращается.

- Откуда: файлы правил (PDF, DOCX, TXT), текст из чата
- Кто пишет: Builder при парсинге
- Когда меняется: только в режиме разработки
- Кто читает: Builder и Game Master (read-only в режиме игры)
- Пример: текст правил боя из книги, таблица оружия, описание рас

### 2. Мозг / правила ИИ (категория `brain`)

Всё что ИИ выстраивает для себя так, как ему удобно. Это не правила игры как таковые, а инструкции для самого себя: как вести игру, в каком порядке создавать персонажа, как обрабатывать бой, какие проверки когда вызывать.

- Откуда: Builder структурирует глоссарий
- Кто пишет: Builder (и только он)
- Когда меняется: только в режиме разработки
- Кто читает: Game Master (read-only в режиме игры)
- Пример: порядок создания персонажа, алгоритм боя, правила маршрутизации ответов (в общий чат или в личный)

Поверх мозга накладываются наши зафиксированные правила платформы (общий чат, личный чат, доступный инструментарий, минимальные обдумывания) — это системный промпт, не данные.

### 3. Игровые данные ИИ (категория `game_hidden`)

Скрытые заметки, планы, идеи, воспоминания Game Master'а. Пишутся постоянно во время игры. Игроки не имеют доступа.

- Откуда: Game Master создаёт по ходу игры
- Кто пишет: Game Master
- Когда меняется: только в режиме игры
- Кто читает: Game Master (и админ для отладки)
- Пример: планы на следующую сцену, заметки о секретах персонажей, саммари прошедших событий, идеи для сюжетных поворотов

### 4. Игровые данные игроков (категория `game_visible`)

То к чему игроки имеют доступ — каждый к своему. Листы персонажей, инвентарь, известная информация. Только Markdown, без инпутов и кнопок. Всё управление — через чат с мастером.

- Откуда: Game Master создаёт и обновляет
- Кто пишет: Game Master (игроки не пишут напрямую)
- Когда меняется: в режиме игры (основное) и при миграциях после разработки
- Кто читает: назначенный игрок (свой лист), Game Master, админ
- Пример: лист персонажа (имя, статы, инвентарь), общая информация о мире (известная всем)

**Листы персонажей — просто MD.** Никаких инпутов, кнопок, drag-n-drop в самих листах. Мы даём Game Master'у инструментарий: читать файлы с формулами, видеть и формулы и результаты, а игрокам показывать только результаты. Если формулы нужны — ИИ решает на этапе построения мозга, как их хранить и применять. Всё взаимодействие игрока с листом — через чат: «повысь мне ловкость на 2», «какой у меня текущий HP?», «использую зелье лечения».

## Система мастеров

Админ может создать несколько мастеров (игр с разными настройками), переключаться между ними. Каждый мастер — своя структура правил, свои сессии, свои игроки. Мастера можно экспортировать как дамп (мозг ИИ-мастера) и загружать/делиться.

---

## Агент 1: Builder (создание мастера)

Работает только с админом в режиме разработки. Задача — из сырых правил собрать всё нужное для игры.

**Вход (загружает админ):**
- Файлы: PDF, DOC, TXT, Markdown
- Текст прямо в чат
- (На будущее) ссылки на вики — с осторожным парсингом

**Что делает:**
- Изучает правила слоями (см. `05-data-strategies.md`), задаёт уточняющие вопросы при противоречиях
- Строит структурированный глоссарий со ссылками на источники и перекрёстными ссылками между документами
- Создаёт README-индекс — навигационный документ по всей структуре (глоссарий + мозг)
- Определяет что есть в игре (листы персонажей, общие листы, инвентарь, навыки…)
- Создаёт шаблоны листов (простой MD, без кнопок/инпутов)
- Задаёт формулы если они нужны (ИИ сам решает нужны ли)
- Настраивает права доступа: что видят игроки, что скрыто
- Создаёт игро-специфичные скилы для Game Master'а
- Готовит индекс правил для быстрого поиска (полнотекстовый + семантический)
- Формирует «мозг» — инструкции для Game Master'а: как вести игру, порядок создания персонажа, обработка ситуаций

**Выход:** структура мастера в БД: документы глоссария, документы мозга, шаблоны, скилы.

**Доработки после запуска:** админ переключает мастера в режим разработки, Builder вносит изменения, формирует сводку изменений. При возврате в режим игры Game Master читает сводку и решает что обновить у игроков.

---

## Агент 2: Game Master (ведение игры)

Работает с игроками в режиме игры. Использует всё что создал Builder. **Не меняет** глоссарий и мозг — только игровые данные (скрытые и видимые).

**Каналы общения:**
- Чат игры (общий) — все игроки + мастер
- Вопрос мастеру (личный) — один на один
- Нейронка маршрутизирует ответы: игровые действия в общий чат, личные вопросы в личный. Игрок пишет в любое поле — агент сам решает куда ответить чтобы не нарушать погружение.
- Шеринг: из личного чата можно поделиться сообщением в общий — появляется компактная строка-событие (как в Telegram) с раскрытием диалога.

**Контекст и память:**
- Первым делом читает README-индекс (`brain`, type=`_index`) — карту всех документов
- Не грузит весь глоссарий в каждый запрос — ищет по мере необходимости
- Ищет по правилам (глоссарий + мозг), листам персонажей, логам
- Держит краткосрочную (текущая сцена) и долгосрочную (саммари) память в `game_hidden`
- Сам решает что загрузить, что не нужно
- Может создавать документы для себя (память, заметки — `game_hidden`), для всех игроков (общая информация — `game_visible`, playerId=null), и для конкретных игроков (личные листы — `game_visible`, playerId=конкретный)
- Документы могут ссылаться друг на друга (`[[document-id]]`), но с соблюдением правил безопасности: игроки не должны через ссылки попасть в `brain` или `game_hidden` (см. `03-architecture.md`)

**Действия игроков:**
- Игрок пишет естественным языком → мастер понимает намерение
- /команды (скилы) с автодополнением, если настроены Builder'ом
- Броски: мастер показывает что кидать, игрок жмёт кнопку
- Админ может настроить авто-броски (одна кнопка = полный расчёт)

**Управление листами:**
- Игрок видит свой лист — просто MD, без инпутов и кнопок
- Все изменения — через чат: «хочу повысить силу», «использую зелье»
- Game Master обновляет лист через инструменты
- Создание новых листов/персонажей — через мастера: «хочу создать персонажа» → мастер ведёт пошагово

## Интерфейс

### Для игрока (максимально просто)

- Слева: сайдбар — чат-навигация (Чат игры, Вопрос мастеру) + контекстные секции (персонаж, шпаргалки, общие листы, сцена)
- Центр: контент текущей страницы (чат, лист персонажа, правило) — каждая страница свой URL
- Чат: аватары (мастер слева, игрок справа), текст, кнопки бросков

### Для админа

- Тот же интерфейс + переключатель режима (разработка/игра) в шапке
- В режиме разработки: чат с Builder'ом для настройки
- В режиме игры: интерфейс как у игрока + доступ ко всем листам и логам
- Доступ к внутренностям: глоссарий, мозг, формулы, логи

## Три типа чатов

### 1. Game Chat — общий чат игры

Один на мастера. Сквозная текстовая история RPG-событий — как книга приключений.

- Видят: все игроки + админы
- Характер: хроника событий, описания сцен, броски кубов
- Сессий: 1 на мастера
- Память: Game Master пишет саммари в `game_hidden` каждые ~20 сообщений
- История: кнопка «Показать всю историю» → paginated view без поля ввода
- Сообщения-события "поделился из личного" — в историю и саммари не попадают

### 2. Personal Chat — личный чат с мастером

Один на игрока (включая админа — у админа тоже свой). Приватные вопросы, создание персонажа, споры о правилах.

- Видят: конкретный игрок + все админы
- Характер: приватные консультации, разбор правил, создание персонажа
- Сессий: 1 на игрока в рамках мастера
- Память: Game Master пишет саммари в `game_hidden`
- Если спор о правилах перерастает в доработку мастера — админ переносит в Builder

### 3. Builder Chat — настройка AI мастера

Один на мастера. Агентный чат где админ и Builder вместе строят глоссарий и мозг.

- Видят: все админы
- Характер: загрузка правил, вопросы, правки, итеративная настройка
- Сессий: 1 на мастера (сквозной, без ветвления)
- Память: Builder пишет саммари в `brain` / `game_hidden`, заметки через `write_note`
- Прикрепление файлов: `.txt` (правила) через документы `Document`

### История и автосаммари

Во всех трёх чатах AI сам ведёт память. Когда история переваливает за ~20 сообщений — пишет саммари (2-3 предложения). При следующем запросе: саммари старых + последние 10 сырых сообщений.

Инструменты AI для памяти: `write_note`, `read_note`, `search_notes`, `search_history` (fallback).

При прокрутке вверх в любом чате — кнопка «Показать всю историю» открывает paginated view без поля ввода. История только содержательные сообщения, без system-событий.

## Сценарии использования

### Админ настраивает мастера (режим разработки)

1. Создаёт игру, переключает в режим разработки
2. Загружает правила
3. Builder изучает, задаёт вопросы, строит глоссарий
4. Builder предлагает структуру (листы, формулы, если нужны)
5. Админ корректирует, задаёт параметры (например: «старт с 6 уровня»)
6. Builder создаёт шаблоны, скилы, индекс, мозг
7. Админ переключает в режим игры
8. Можно приглашать игроков

### Игрок создаёт персонажа (режим игры)

1. Пишет в личку: «помоги создать персонажа»
2. Game Master смотрит мозг (порядок создания), глоссарий (правила), параметры админа
3. Ведёт пошагово (в D&D: раса → класс → статы → навыки; в другой игре — иначе)
4. Заполняет данные, применяет формулы (если есть), проверяет по правилам
5. Создаёт `game_visible` документ — лист персонажа
6. Игрок видит готовый лист

### Игровой процесс (пример D&D)

1. Мастер описывает сцену в общем чате
2. Игрок в личке: «пытаюсь незаметно пробраться за спину стражника»
3. Мастер ищет правило скрытности в глоссарии/мозге
4. Предлагает бросок: кнопка «Скрытность (D20 + 5)»
5. Игрок жмёт — результат
6. Мастер описывает исход (публично или скрытно)
7. При необходимости просит другого игрока «сделай проверку восприятия» не объясняя зачем

### Админ дорабатывает во время кампании

1. Нашёл ошибку или хочет дополнить правила
2. Переключает мастера в режим разработки
3. Builder анализирует что затронуто, вносит изменения
4. Builder формирует сводку: «поменялось правило скрытности, затронуты листы: эльфы (+2 вместо +1), воры (новый навык)»
5. Админ переключает обратно в режим игры
6. Game Master читает сводку → решает обновить листы эльфов и воров
7. Вносит изменения через инструменты обновления
8. Игра продолжается
