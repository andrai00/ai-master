# План: модель уникальных путей документов (links by path + portable save)

> Дата: 2026-08-21. Статус: **план согласован, готов к реализации. Не начато.**
> Контекст: ссылки `[[<UUID>|<label>]]` ломаются после загрузки сохранения в новую игру, потому что импорт создаёт документы с новыми UUID. Переходим на **уникальные пути** как ЕДИНСТВЕННЫЙ способ ссылок — так, как Cursor/Claude работают с файлами.
>
> **Решение зафиксировано (2026-08-21):** чистые пути, **без легаси**. Ссылки только `[[<path>|<label>]]`; id в сохранении НЕ пишутся; фолбэка по id НЕТ; старые сохранения пользователь переделает сам. Открытых вопросов нет — всё либо делаем, либо не делаем.

---

## 1. Проблема

- Ссылки в чате и документах = `[[<UUID>|<label>]]` — зашиты id.
- Импорт сохранения (`bulk-import`) создаёт документы с **новыми** UUID → старые ссылки мертвы («Document not found»).
- Игр может быть несколько; при этом UUID документов могут **совпадать между играми** (одно сохранение → две игры). Это безопасно, т.к. все запросы фильтруют по `masterId` — но **id в сохранении не нужны**: переносимая идентичность документа = путь.

---

## 2. Одна трасса — модель путей

| | Решение |
|---|---|
| Ссылки | `[[<path>|<label>]]` — только пути, без id |
| Импорт/экспорт | сохраняется **только `path`** (и данные: category/type/title/summary/content/tags/playerId); `id` генерируются заново при импорте |
| Резолвер | по `path` (индекс), нормализация `/`, `.md`, `#anchor`; **без фолбэка по id** |
| Переименование | `rename_document(id, new_path)` с каскадом ссылок |
| Права | по префиксу пути |
| Легаси | нет — старые сохранения переделываются |

## 3. (Удалено) Трасса A

Отклонена решением от 2026-08-21: никакого сохранения id и никакого фолбэка по id — только чистые пути.

## 4. Модель уникальных путей

### 4.1. Структура пути

```
glossary/homebrew/articles/bestiary/210-curse_of_wandering
glossary/bestiary/331-camel
glossary/rules/mechanics/158-movement_and_position
brain/routing/main-router
hidden/memory/scene-3
visible/<playerId>/sheet-valera
```
- **Категория — ВСЕГДА первый сегмент** для всех категорий, включая глоссарий: `glossary/...`, `brain/...`, `hidden/...`, `visible/{playerId}/...`.
- **Источник** — папки из исходного архива (`homebrew/articles/bestiary/`).
- **Файл** — имя без `.md`.
- Отдельное поле `type` остаётся смысловым (monster/spell/rule): **путь = откуда, type = что это**.
- **id модели НЕ показываются** — в промптах, дереве, поиске и ссылках только пути.

> **Внутренние ссылки архива (без префикса, `/bestiary/331-camel.md`):** в корпусе они без `glossary/`. Пост-обработка 8000 файлов НЕ нужна: резолвер при клике ссылки из glossary-документа **сам пробует `glossary/<путь>` первым** (затем категорию ссылающегося документа). Это логика резолва, а не изменение данных.

### 4.2. Уникальность

- Колонка `Document.path` + уникальный индекс `[masterId, path]` — путь уникален **в рамках игры** (как id).
- **Коллизии:** в одном чистом импорте одинаковых путей не бывает (файловая система гарантирует уникальность). Реальные источники коллизий:
  1. нормализация имён (регистр/спецсимволы схлопывают разные пути в один);
  2. повторный импорт/мерж в ту же игру (пути из второго сохранения заняты);
  3. пути, придуманные ИИ для `brain/`/`hidden/`/`visible/` (может выбрать занятый).
- Разрешение: детерминированный суффикс (`goblin`, `goblin-2`, `goblin-3`), назначаемый **по порядку появления документа в JSON** — повторная загрузка того же сохранения даёт те же суффиксы (иначе ссылки снова ломаются).

### 4.3. Ссылки

- Формат: `[[<path>|<label>]]` в чате и документах — **только пути, без id**.
- Резолвер: по `path` (индекс), нормализация `/`, `.md`, `/`, `#anchor`. Порядок: точный путь → авто-`glossary/` для ссылок из glossary-документов (внутренние архивные ссылки) → по префиксу категории.
- Чат — история, не переписывается при переименованиях; битые ссылки в старом чате допустимы.
- Перекрёстные ссылки между категориями — только явным префиксом (`brain/...` → `glossary/bestiary/331-camel`).

### 4.4. Права по префиксу пути (read + write)

Права распространяются на ВСЕ инструменты (чтение и запись), не только read-тулы. Консолидируются read-тулы (3 шт.), write-тулы остаются доменными — но проверка прав единая: по префиксу пути.

| Префикс | Builder (brain) | Builder (memory) | GM game | GM personal | Player |
|---|---|---|---|---|---|
| `glossary/` | read/write | read | read | read | read |
| `brain/` | read/write | read | read | read | — |
| `hidden/` | read | read/write | read/write | read | — |
| `visible/{playerId}/` | read | read/write | read/write | read/write | read (свой) |

- И Builder, и GM знают эти правила из промпта; тул дополнительно отклоняет нарушение с понятной ошибкой.
- Пример из текущего поведения (сохраняется): личный и общий чат читают `glossary/`, но **не редактируют**; `hidden/` — только мастер/билдер memory-режима.
- Ограничения понимаются одинаково и в коде (проверка префикса), и моделью (описания тулов + промпт).

### 4.5. Переименование с каскадом (`rename_document`)

- `update_document` **запрещает** менять путь (иначе теряется каскад).
- **Каскад универсален — работает для ВСЕХ деревьев**, не только глоссария. Любой документ любой категории может ссылаться на любой другой:
  - перекрёстные ссылки — явным префиксом (`hidden/notes/x` → `[[glossary/bestiary/331-camel]]`, `brain/...` → `[[hidden/memory/scene-3]]`);
  - внутри глоссария — и явные `[[glossary/...]]`, и архивные без префикса (`/bestiary/331-camel.md`);
  - внутри brain/hidden/visible — явными `[[путь]]`.
  Поэтому каскад сканирует `Document.content` ВСЕХ категорий.
- Отдельный тул `rename_document(id, new_path)`:
  1. проверка свободности `new_path`;
  2. атомарно (транзакция): обновить путь;
  3. **каскад** — обновляет ОБЕ формы токена во всех `Document.content` по **точным границам** (`[[`, `]]`, `|`, пробел/конец строки):
     - явную: `[[glossary/папка/пример_документа` → `[[glossary/папка/новое_имя`;
     - архивную (внутри глоссария): `/папка/пример_документа.md` / `/папка/пример_документа/` → `/папка/новое_имя...`.
     `пример_документа_2` не затрагивается;
  4. обновить `DocumentRead` при необходимости.
- **Модель видит только форму с `glossary/`**: в БД хранится оригинал (архивные ссылки без префикса, данные не переписываются), но `read_document` при возврате контента **нормализует ссылки на лету** (`/папка/файл.md` → `glossary/папка/файл`). Внешние `/...` (CDN и пр.) не трогаются. Итог: хранение = как в архиве, чтение/отображение = с `glossary/`, каскад знает обе формы.

### 4.6. Импорт/экспорт

- Экспорт включает `path` каждого документа (и данные: category/type/title/summary/content/tags/playerId). **`id` в JSON не пишется.**
- Импорт: `path` восстанавливается из JSON (не пересчитывается!) + детерминированное разрешение коллизий; `id` генерируются заново (уникальны в рамках игры).
- То же сохранение → любая игра → те же пути → ссылки в документах работают. Совпадение id между играми невозможно/неважно — их в сохранении нет.

### 4.7. Промпты

- Билдер: «ссылайся по пути `[[<path>|<label>]]`, путь бери из результатов search_documents/read_document/list_documents; перед созданием — поиск, дубликаты отклоняет тул».
- `list_documents` возвращает **дерево путей** (как Explorer в Cursor).
- **Следование по ссылкам:** «если в документе встретилась ссылка `[[путь|...]]` и нужно её содержимое — открой её через `read_document("<путь>")`».
- **Ссылки во всех создаваемых документах:** «в ЛЮБОЙ создаваемый документ (brain-секция, hidden-заметка, лист, статья) добавляй `[[путь|подпись]]` на связанные документы — используя пути, уже известные из контекста (результаты поиска/чтения/дерева), без специальных лишних поисков».
- **Мозг:** всегда `_index` + короткие `summary` + перекрёстные ссылки секций на `glossary/...` и между секциями.
- **Создание vs изменение (защита от перезаписи):** уникальный индекс `[masterId, path]` + проверка в туле. `create_document(path)` при занятом пути ОТКЛОНЯЕТ с ошибкой (путь, title, id существующего) — перезапись через create невозможна. Изменение существующего — только `update_document` (явное действие). Замена чужого/важного контента (глоссарий, заданные извне brain-секции, листы игроков) — только с подтверждением админа (существующее правило); свои рабочие файлы (`hidden/memory/`, собственные заметки) агент обновляет без спроса.

### 4.8. Миграция существующих данных

- Разовый скрипт: вывести `path` из title (часть до « — ») или из `type`+title; коллизии — детерминированный суффикс; заполнить `Document.path`.
- Легаси-ссылок по id не поддерживаем — существующие id-ссылки в документах не переносим; старые сохранения переделываются пользователем. (Внутренние архивные ссылки `/bestiary/331-camel.md` уже путь-совместимы.)

### 4.9. Внутренние ссылки архива (факты из ai-dnd, 8592 файла)

Разобран корпус `C:\Users\avg\Desktop\ai-dnd`:

- **Основной формат внутренних ссылок** — абсолютные пути от корня архива: `/bestiary/331-camel.md`, `/spells/203-burning_hands.md`, `/rules/mechanics/158-movement_and_position.md`, `/homebrew/spells/5955-gravity_barrier.md`, `/homebrew/articles/bestiary/210-curse_of_wandering.md`.
- **Без префикса `glossary/`**; часть путей с `rules/`, большинство без; бывают с `.md`, бывают с `/` на конце (`/spells/149-ray_of_frost/`), бывают с `#якорь`.
- `[[...]]` в корпусе — **декоративный текст внутри markdown-ссылок**, а не вики-ссылки (настоящих `[[...]]` нет).
- Относительные ссылки без `/` в корпусе — это внешние `https://` (их не трогаем).
- **Все внутренние ссылки ведут только на другие файлы того же архива (глоссарий).** Внешние ссылки остаются как есть.

Выводы:
1. Путь импортированного документа = `glossary/` + путь от корня архива → внутренние ссылки резолвятся через авто-`glossary/` без пост-обработки.
2. Резолвер для ссылки из glossary-документа ищет только в glossary текущей игры.
3. `replace_wiki_links` (переписывание ссылок при импорте) становится **не нужен** — экономия на 8000 файлов.
4. **Ссылки на чаты** уже в отдельном формате `:nav-game:` / `:nav-personal:` (`remarkChatLink` → `ChatNavLink` → `next/link`) — не пересекаются с путями документов.

### 4.10. Память мастера (ранее «auto memory») — решение: делаем (этап после путей)

Скрытая память `hidden/` и есть место для памяти мастера — **четырёхкатегориальная модель не меняется** (`glossary`/`brain`/`game_hidden`/`game_visible` остаются; «память мастера» = структура внутри `game_hidden`, а не пятое хранилище).

- **Сейчас (сыро):** заметки — ad-hoc документы `hidden/notes/...` без правил; агент пишет что попало.
- **Предложение:** конвенция `hidden/memory/`:
  - `hidden/memory/index` — короткий индекс «что помню» (грузится в прелоад каждую сессию, как MEMORY.md);
  - `hidden/memory/players` — по игрокам (предпочтения, события);
  - `hidden/memory/scenes` — хронология и решения сцен;
  - `hidden/memory/decisions` — ключевые решения мастера и почему;
  - секции читаются по требованию (как `get_brain(topic)`).
- Агент ведёт их по ходу игры; после сжатия контекста индекс + секции ре-инжектятся.
- Секции подстраиваются под ролевку (DnD / Cyberpunk / Ктулху — разные разделы).
- **Структуру памяти определяет Builder из правил:** изучив глоссарий, Builder решает, какие секции памяти нужны мастеру ЭТОЙ игры (для DnD — персонажи/фракции/локации; для магической системы — школы/артефакты/ритуалы; для Ктулху — рассудок/культы), и описывает это в brain-секции **«Память мастера: как её вести»** (`brain/memory_management`) — структура, когда писать, когда архивировать. Это политика → её место в `brain/`.
- **GM** читает brain-секцию «Память мастера» и ведёт `hidden/memory/*` по ней; если секции нет — ведёт по минимуму (игроки, сцены, решения).
- **Индекс-файл для памяти НЕ нужен** (отдельного `_index` нет — прелоад авто-перечисляет реальные секции с `summary`). Роль «индекса» выполняет brain-секция: шаблон/политика структуры, а прелоад показывает фактическое состояние.
- **Прелоад:** авто-перечисление секций `hidden/memory/*` (title + `summary`) — как мозг, БЕЗ отдельного `_index` (нечему устаревать). Игрокам `_index` не нужен вовсе (`get_players`/`get_player_sheet` дают живые данные).
- **Самари чата — не дублировать:** это `ChatSummary` (таблица), не документ. Секции памяти имеют только короткие `summary`-аннотации.
- **Оценка четырёх категорий — подходят.** Роли непересекающиеся: `glossary` (внешние правила), `brain` (процедуры мастера), `game_hidden` (приватная память), `game_visible` (данные игрока). Единственный стык — чёткая граница `brain` vs `game_hidden`: `brain/` = системные политики ведения (стабильны), `hidden/` = факты/решения конкретной игры (динамичны). Задаётся в промптах.
- **Улучшение «мозга» (не схема, а поведение Builder):** всегда `_index`, короткие `summary`, перекрёстные ссылки секций на `glossary/...` и между секциями.
- **Ссылки:** ИИ следует по `[[путь|...]]` через `read_document`; ссылки добавляются во все создаваемые документы из уже известных путей.
- **Решено — границы записи (против дублей):**
  - `hidden/memory/` — долговременные значимые факты: персонажи, решения, события, меняющийся тон;
  - `hidden/notes/` — временные заметки текущей сцены (промежуточные);
  - `visible/` — то, что должен ВИДЕТЬ игрок (листы, корабль, лут, настройки).
- **Решено — авто-рефакторинг:** при разрастании секции (правило в brain-политике, например > 50 записей) агент сжимает старые сцены/события в `hidden/memory/archive` (история), чтобы рабочая память не пухла.

### 4.11. Модель знаний — валидация (обсуждено)

Модель четырёх категорий подтверждена и совпадает с логикой старой программы:

| Понятие пользователя | Категория | Роль |
|---|---|---|
| Правила | `glossary` | внешний корпус любых правил (DnD, Starfinder, Cyberpunk, мафия…) |
| Мозг | `brain` | вытянуть важное: индекс + «горячие» правила + политики |
| Память | `game_hidden` | события, факты, идеи, меняющийся тон игры |
| Открытые карточки | `game_visible` | листы персонажей, корабль, лут, настройки — видно игрокам (playerId null = общее) |

**Уточнения (без изменения схемы):**
1. **«Горячие/холодные» правила:** частые (преимущество/помеха, базовые проверки) — секции мозга (в прелоаде); редкие (предметы, альтернативные правила) — НЕ в мозг, в индексе правило: «редкие/списки — через поиск (`search_documents`)». Прописать жёстко в промпте Builder. Это НЕ конфликт с консолидацией read-тулов: консолидация обобщает ~8 тулов в 3 (`list_documents`/`read_document`/`search_documents`), а не убирает поиск — `search_rules` становится `search_documents` (поиск по всем категориям с фильтром category/type).
2. **Стиль ведения:** стабильный (нарратив, темп, доменные правила) → мозг; меняющийся тон кампании → память. Граница `brain`/`hidden` = «стабильное vs динамичное».
3. **Имена:** коды категорий не меняем; в UI/промптах — человеческие имена «Правила / Мозг мастера / Память мастера / Открытые карточки».

## 5. Честные риски / обсуждение

- **Путь vs type**: путь — источник, type — смысл. Промпт и дерево снимают путаницу, но нужно аккуратно объяснить модели.
- **Длинные пути** в контексте — чуть больше токенов, чем UUID (незначительно).
- **Чат не переписывается** при переименованиях — битые ссылки в истории остаются.
- **Детерминизм суффиксов** при импорте — критичен, иначе повторная загрузка ломает ссылки.
- **Без легаси**: старые id-ссылки не поддерживаем — пользователь переделывает сохранения; миграция выводит пути из title.

## 6. Решённые вопросы (все закрыты)

1. **`path` как колонка или из title?** — колонка `Document.path` + уникальный индекс `[masterId, path]`; миграция выводит пути из title (до « — »).
2. **Старые ссылки id → path при миграции?** — без легаси: id-ссылки не поддерживаем, сохранения переделываются пользователем.
3. **Переписываем ли ссылки в чате при переименовании?** — нет, чат — история; переписываются только документы.
4. **Детерминизм коллизий?** — суффикс `-2` по порядку появления в JSON.
5. **Ссылки по id параллельно с путями?** — нет, только пути.
6. **`rename_document` в интерфейсе (кнопка) или только тул для ИИ?** — только тул для ИИ (через чат); отдельная кнопка не делается.

## 7. Порядок работ

1. Колонка `path` + миграция существующих данных → резолвер по пути → промпты → `list_documents`-дерево → консолидация read-тулов → `rename_document` с каскадом → импорт/экспорт путей → (этап) память мастера → FTS5 → промпт-кэш/дефер схем → субагенты.

## 8. Дорожная карта и решения (перенесено из 08)

### 8.1. Как модель ищет на любых языках (принцип)

Современная нейронка (как Claude/GPT/DeepSeek) — **многоязычная**: понимает запрос и на русском, и на английском. Поиск по документам зависит от механизма:

- **Ключевой поиск (`LIKE`/FTS5)** — ищет ТОЧНЫЕ слова. Модель сама переводит запрос на язык документа перед поиском (знает оба языка), поэтому кросс-язык **работает, но хрупко**: надо угадать словарный запас документа.
- **Семантический (эмбеддинги)** — многоязычные векторы отображают «урон огнём» и «fire damage» в близкие точки пространства → поиск по смыслу **работает кросс-язык без перевода**.
- **Гибрид (рекомендуется)** — модель расширяет/переводит запрос для ключевого поиска + семантический ретривал поверх.

Как делают агенты: Cursor — индекс кода + эмбеддинги (семантика); Claude Code / Kilo — grep/ключевые тулы + понимание модели (без эмбеддингов в CLI); многоязычность обеспечивает сама модель. То есть **у нас уже есть «поиск на любых языках»** через ключевой поиск (`search_rules`, после консолидации — `search_documents`) + переводящую модель; эмбеддинги делают это устойчивым, но в план не входят.
