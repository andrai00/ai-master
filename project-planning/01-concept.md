# Концепция

## Общая идея

Универсальный ИИ-мастер, которого админ настраивает под любую настольную ролевую игру. Два агента: **Builder** помогает админу создать/настроить мастера, **Game Master** ведёт игру с игроками.

Интерфейс — подобие Notion/Obsidian: слева дерево папок/файлов, в центре вкладки с чатами и листами. Всё файловое, БД только для служебных данных (см. `03-architecture.md`).

Проект не привязан к D&D. Все примеры с D&D — просто иллюстрации; система должна одинаково хорошо работать с Fate, Vampire, Call of Cthulhu, PbtA, самописными системами и т.д.

---

## Агент 1: Builder (создание мастера)

Работает только с админом. Задача — из сырых правил собрать всё нужное для игры.

**Вход (загружает админ):**
- Файлы: PDF, DOC, TXT, Markdown
- Текст прямо в чат
- (На будущее) ссылки на вики — с осторожным парсингом

**Что делает:**
- Изучает правила слоями (см. `05-data-strategies.md`), задаёт уточняющие вопросы при противоречиях
- Строит структурированный глоссарий со ссылками на источники
- Определяет что есть в игре (листы персонажей, общие листы вроде корабля, инвентарь, навыки…)
- Создаёт шаблоны листов
- Задаёт формулы если они нужны
- Настраивает права доступа: что видят игроки, что трогать нельзя
- Настраивает /команды, подсказки, кнопки бросков
- Создаёт игро-специфичные скилы для Game Master'а
- Готовит индекс правил для быстрого поиска

**Выход:** структура папок мастера (см. `glossary.md` — каноническая структура).

**Доработки после запуска:** админ может вернуться и поправить мастера даже во время идущей игры. Builder делает миграцию: понимает что затронуто, помечает, предлагает обновить (см. `07-open-questions.md` — миграции пока сложный вопрос).

---

## Агент 2: Game Master (ведение игры)

Работает с игроками. Использует всё что создал Builder. **Не меняет** правила и шаблоны — только сессионные данные.

**Каналы общения:**
- Личный чат с каждым игроком
- Общий чат (виден всем)
- Скрытые действия: игрок в личке делает что-то, мастер в личке другому игроку просит проверку не раскрывая причину

**Контекст и память:**
- Не грузит все правила в каждый запрос — ищет по мере необходимости
- Ищет по правилам, листам персонажей, логам
- Держит краткосрочную (текущая сцена) и долгосрочную (саммари) память
- Сам решает что загрузить, что не нужно

**Действия игроков:**
- Игрок пишет естественным языком → мастер понимает намерение
- /команды (скилы) с автодополнением, если настроены
- Броски: мастер показывает что кидать, игрок жмёт кнопку
- Админ может настроить авто-броски (одна кнопка = полный расчёт)

**Управление листами:**
- Игрок видит свой инвентарь, может перемещать предметы (drag-n-drop)
- Создание новых листов/сущностей — только через мастера
- «Хочу создать персонажа» → мастер ведёт пошагово, или сам предлагает если у игрока нет персонажа

## Интерфейс

### Для игрока (максимально просто)

- Слева: дерево доступных файлов
- В центре: вкладки — чат, лист персонажа, общий лист (корабль и т.п.)
- Чат: текст, подсветка /команд, кнопки бросков
- Листы: красивые Markdown-страницы, **формулы скрыты**
- Игрок видит результат, не видит математику. Спросит «почему?» — мастер объяснит текстом

### Для админа

- Тот же интерфейс + больше доступа
- Чат с Builder'ом для настройки
- Доступ к внутренностям: правила, формулы, логи
- Правки на лету, запуск миграций

## Сценарии использования

### Админ настраивает мастера

1. Загружает правила
2. Builder изучает, задаёт вопросы, строит глоссарий
3. Builder предлагает структуру (листы, формулы)
4. Админ корректирует, задаёт параметры (например: «старт с 6 уровня»)
5. Builder создаёт шаблоны, скилы, индекс
6. Можно приглашать игроков

### Игрок создаёт персонажа

1. Пишет в личку: «помоги создать персонажа»
2. Game Master смотрит правила, шаблон, параметры админа
3. Ведёт пошагово (в D&D: раса → класс → статы → навыки; в другой игре — иначе)
4. Заполняет данные, применяет формулы, проверяет по правилам
5. Игрок видит готовый лист

### Игровой процесс (пример D&D)

1. Мастер описывает сцену в общем чате
2. Игрок в личке: «пытаюсь незаметно пробраться за спину стражника»
3. Мастер ищет правило скрытности
4. Предлагает бросок: кнопка «Скрытность (D20 + 5)»
5. Игрок жмёт — результат
6. Мастер описывает исход (публично или скрытно)
7. При необходимости просит другого игрока «сделай проверку восприятия» не объясняя зачем

### Админ дорабатывает во время кампании

1. Нашёл ошибку в правилах
2. Builder анализирует что затронуто (листы, формулы, память)
3. Помечает, предлагает миграцию
4. Админ подтверждает — миграция выполняется
5. Игра продолжается
